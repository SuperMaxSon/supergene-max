이 표가 중요한 이유

코지의 1010은 번들 다운로드와 인스턴스화가 끝나기 전에 찍힙니다. 즉 코지 3.04초에는 "게임 화면이 뜨기까지"의 비용이 들어있지 않습니다. 반대로 솔리테어 NRU 5.17초에는 그게 다 들어있죠. 따라서 실제 체감 격차는 표에 찍힌 +2.13초보다 큽니다. 숫자를 그대로 "코지가 2초 빠르다"로 옮기면 과소평가입니다.

그래도 이 지표를 쓰는 이유

1010의 $.time 필드는 5개 클라 모두 동일한 계산식(Date.now() - window.startTime)이라 조인 없이 한 행으로 값이 나옵니다. 세션 키를 맞출 필요가 없어 집계 오류가 끼어들 여지가 가장 적습니다. 결승선 차이만 인지하고 쓰면 "최소한 이만큼은 느리다"의 하한선으로는 충분히 유효합니다.

④ 빌드가 섞였다. 08-06~08-08 창 안에서만 로딩 코드가 두 번 바뀌고 롤백까지 있었습니다5. 날짜로 자르면 서로 다른 빌드가 한 셀에 들어갑니다.

축을 날짜에서 client_version으로 바꾼다. 배포 경계에서 값이 딱 갈리면 우리 변경 효과가 맞고, 안 갈리면 요일·회선 노이즈였던 겁니다. 이게 결정적입니다.

이 표의 한계 2가지 — 확정 수치가 아닙니다

① 중앙값의 차 ≠ 차의 중앙값. 이벤트별로 독립적으로 낸 p50이라 뺄셈이 정확하지 않습니다. 실제로 퍼블마 NRU는 ALL_LOAD_FB → 1010이 5.56초로 나오는데, 같은 기간 1010.$.time p50(4.34초)보다 큽니다 — 앞뒤가 안 맞습니다. 확정하려면 플레이어별 차이의 중앙값으로 다시 뽑아야 합니다. 지금 표는 방향과 크기를 잡는 용도입니다.

② 생존자 편향. 기준점이 2100이라 판을 시작한 세션만 들어 있습니다. 로딩 도중 이탈한 유저는 통째로 빠졌으므로 실제 로딩 체감은 이 숫자보다 나쁩니다.

iOS 유저는 기기·회선이 대체로 좋습니다. 코지는 iOS가 과반이고 솔리테어는 안드로이드가 69%이니, 단순 평균 비교는 이 차이에 오염돼 있습니다.

다만 OS를 맞춰도 배율이 2.5배로 같습니다. 믹스를 걷어내도 솔리테어가 2.5배 느리다는 뜻이라, 격차의 원인은 유저 구성이 아니라 빌드 구조입니다. 반대로 말하면, 안드로이드 비중이 높은 것 자체는 고칠 수 없으니 구조를 고쳐야 그 몫까지 같이 좋아집니다.

이미지 선주입 3.0MB 가설 — 기각은 아니고 "꼬리 전용"으로 격하

솔리테어는 부팅 시점에 인게임 이미지 6장(원본 합계 3.0MB)을 iOS는 preload, 안드로이드는 prefetch로 주입합니다. PNG은 이미 압축된 포맷이라 전송 단계에서 더 줄지 않습니다 — 느린 회선에서는 이 3.0MB가 그대로 파이프를 먹습니다.

그런데 주입 방식이 정반대인 두 OS에서 배율이 2.5배로 동일합니다. 이게 주범이면 고우선순위로 끼어드는 iOS가 더 나빠야 합니다. 중앙값에서는 영향이 안 보이므로 꼬리(느린 회선) 전용 가설로 내려둡니다. 완전 기각은 아닙니다 — 솔리테어가 무너지는 구간이 정확히 그 꼬리입니다.

로컬 저사양 계측은 중앙값이 아니라 꼬리를 재고 있었다

사내 로컬 프로파일(CPU 10.8배 저하 + Fast 4G)에서 이 구간은 약 5.8초(index.js 3.2초 + 씬 2.6초)로 측정됐습니다. 라이브 필드 p50은 0.97초로 약 1/6입니다.

둘 다 맞는 값입니다 — 로컬 프로파일이 재고 있던 건 저사양 세그먼트, 즉 p90 이상의 꼬리입니다. 개선 판단을 로컬 수치로만 하면 중간 유저 기준으로는 과대평가, 반대로 필드 p50만 보면 가장 아픈 세그먼트를 놓칩니다. 두 숫자를 같이 봐야 합니다.

① "이름만 NRU"인 로그가 데이터로 확정됐다

퍼블마 2150_GAMEPLAY_NRU_PLACE1은 이름에 NRU가 붙어 있지만 게이트가 "첫 배치"뿐이라 전체 유저에게 찍힙니다. 실제로 RU 판의 69.1%에서 발화합니다.

대조적으로 진짜 게이트가 걸린 2151_GAMEPLAY_NRU_PLACES는 RU에서 5.4%, 솔리테어 2150_GAMEPLAY_NRU_CARD_MATCH는 RU에서 아예 안 잡힙니다(임계 미만). 이름만 보고 NRU 지표로 쓰면 전체 유저 수치를 신규 유저 수치로 착각합니다.

② 순서 역전이 두 곳에서 그대로 재현됐다

퍼블마는 NRU 튜토 로그가 전부 음수(-22.0 ~ -0.25초)로 나옵니다 — 2100보다 앞이라는 뜻이고, 코드 감사에서 찾은 "튜토를 다 끝낸 뒤 2100을 찍는다"와 일치합니다. 퍼블마의 "판 시작"은 사실 튜토가 끝난 시점이라, 다른 프로젝트의 2100과 같은 의미로 쓰면 안 됩니다.

솔리테어 NRU는 1010이 2100보다 +0.03초 뒤입니다(각주 6).

③ 튜토 완료를 못 재는 프로젝트가 둘

코지·마종은 튜토 노출만 있고 완료 로그가 없습니다 — 어디서 이탈했는지 못 잡습니다. 솔리테어는 둘 다 있어서 계산이 되는데, 노출 91% 대비 완료 61%로 튜토 완주율 약 67%입니다.

첫 판 완주율(2300)은 퍼블마 84% > 솔리테어 59% > 코지 51%입니다. 로딩이 가장 빠른 코지가 완주율은 가장 낮습니다 — 로딩 속도와 초반 이탈은 같은 방향이 아닙니다.

④ 이 표를 퍼널로 쓰면 안 되는 이유

골격(시작→튜토→입력→성과→종료→결과)은 5개가 같지만 같은 칸에 들어가는 번호가 전부 다릅니다. 첫 입력은 4가지 (9990/2115/9995/없음), 첫 성과는 3가지(2130/2120/2150)입니다.

번호가 같아도 뜻이 다른 경우가 있습니다 — 2510은 솔리테어에선 입장료, 마종에선 보상 수령입니다. 11001은 솔리테어가 레벨 6 도달, 코지·마종은 누적 클리어 5회입니다. 이름으로 합치면 서로 다른 사건을 더하게 됩니다.

사용한 쿼리 (A안 — 로딩 총량) 
WITH raw_log AS (
  SELECT 'SCJ' AS g, log_date, player_id, logincount_total, event, data, log_time
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date BETWEEN '2026-08-08' AND '2026-08-10'
    AND (is_dev = FALSE OR is_dev IS NULL) AND player_id > 0 AND country = 'US'
  UNION ALL
  SELECT 'COZY', log_date, player_id, logincount_total, event, data, log_time
  FROM `game-log-359704.raw.cozy_tiles`
  WHERE log_date BETWEEN '2026-08-08' AND '2026-08-10'
    AND (is_dev = FALSE OR is_dev IS NULL) AND player_id > 0 AND country = 'US'
  UNION ALL
  SELECT 'PBM', log_date, player_id, logincount_total, event, data, log_time
  FROM `game-log-359704.raw.puzzle_block_master`
  WHERE log_date BETWEEN '2026-08-08' AND '2026-08-10'
    AND (is_dev = FALSE OR is_dev IS NULL) AND player_id > 0 AND country = 'US'
),
load_done AS (
  SELECT g,
         IF(logincount_total <= 1, 'NRU', 'RU') AS seg,
         player_id,
         CAST(JSON_VALUE(data, '$.time') AS INT64) / 1000 AS load_sec
  FROM raw_log
  WHERE event = '1010_LOAD_COMPLETE'
    AND JSON_VALUE(data, '$.time') IS NOT NULL
  QUALIFY ROW_NUMBER() OVER (PARTITION BY g, player_id ORDER BY log_time) = 1
),
agg AS (
  SELECT g, seg,
         COUNT(*) AS n,
         AVG(load_sec) AS avg_sec,
         APPROX_QUANTILES(load_sec, 100)[OFFSET(50)] AS p50,
         APPROX_QUANTILES(load_sec, 100)[OFFSET(90)] AS p90
  FROM load_done
  WHERE load_sec BETWEEN 0 AND 600
  GROUP BY 1, 2
)
SELECT g, seg, n,
       ROUND(avg_sec, 2), ROUND(p50, 2), ROUND(p90, 2),
       ROUND(p50 - MAX(IF(g = 'COZY', p50, NULL)) OVER (PARTITION BY seg), 2)
FROM agg
ORDER BY seg, p50

각주

판정 근거 — 모두 각 리포 main 브랜치 코드 실측

1 — 코지의 1010은 화면과 무관하다

LogManager.logLoginComplete() 안에서 로그인 로그 응답 Promise에 setTimeout 100ms를 걸어 logLoadComplete()를 호출합니다. 인게임을 띄우는 건 완전히 다른 병렬 링크(requestStart)라 1010과 2100의 선후는 회선·기기에 따라 뒤집힐 수 있습니다 — 코드만으로는 부호를 확정할 수 없고, 데이터로 확인해야 합니다.

2 — 솔리테어 RU는 프리레벨 팝업이 결승선

PopupGameEntry.onShowStart에서 logLoadComplete()를 부르고, 바로 다음 줄에서 2090_PRE_LEVEL_SHOW를 찍습니다. 즉 RU의 1010은 유저가 Play를 누르기 전 시점입니다.

3 — 솔리테어 NRU는 2100이 1010보다 앞선다

레벨 1~2는 로비를 건너뛰고 인게임으로 직행합니다. prepareGame()에서 2100을 찍은 뒤 view.show() → onShowStart에서 1010이 찍히므로 순서가 뒤집혀 있습니다. 두 로그의 시간차는 1프레임 수준입니다.

4 — RU 경로 비용은 가설에서 확인으로 v1.1 갱신

솔리테어 RU는 로비 번들 프리로드 + 친구 리더보드 조회(soft timeout 3초) + 프리레벨 팝업 로드를 거칩니다. 초판에서는 "구조상 그럴 것"이라는 가설이었으나, 구간 분해에서 RU 인트로가 NRU의 1.7배(4.72 vs 2.69초)로 확인됐습니다. 다만 세 요소 중 어느 것이 얼마를 먹는지는 아직 분해되지 않았습니다 — INTRO_* 쌍으로 추가 분해가 가능합니다.

5 — 08-06~08-08 창의 빌드 혼재

해당 기간 커밋: f1ec06b7 인게임 이미지 선주입 제거 → aec765e4 같은 변경 롤백 → 690edc36 밸런스시트 로딩 fetch 전환 및 4xx 즉시 포기(인트로 403 스톨 해소) → 76fa97bf 프리로드 지면 확대. 배포 반영 시점은 커밋일과 다르므로 client_version으로 확인해야 합니다.

6 — 순서 역전이 데이터로 확인됨 v1.1 추가

구간 분해에서 솔리테어 NRU의 1010이 +0.03초로 나옵니다 — 2100보다 뒤입니다. 각주 3의 코드 판정(1프레임 수준 역전)이 라이브 데이터로 그대로 확인됐습니다. 퍼블마 NRU의 튜토 로그가 전부 음수(-22 ~ -0.25초)로 나오는 것도 튜토가 2100보다 앞이라는 감사 결과와 일치합니다.

7 — 압축은 다운로드만 줄인다 v1.2 추가

페이스북은 스크립트를 brotli로 전송 압축하므로 빌드에서 보이는 원본 크기로 다운로드 이득을 계산하면 과대평가됩니다(main index.js 원본 3.02MB → 전송 638KB). 반대로 PNG은 이미 압축된 포맷이라 전송에서 거의 안 줄어듭니다(실측 −1.6%) — 텍스트에만 성립하는 명제를 이미지에 적용하면 안 됩니다.

그리고 파싱 비용은 압축과 무관하게 원본 크기 기준입니다. 그래서 "전송은 638KB니까 가볍다"와 "파싱은 3.02MB치"가 동시에 참입니다.

8 — 이미지 선주입 제거는 한 번 시도됐다가 롤백됐다 v1.2 추가

2026-08-06 저녁 부팅 이미지 주입 블록을 제거했다가 다음 날 아침 롤백했습니다. 사유는 "제거 근거였던 이중 다운로드가 실제로는 발생하지 않음" — 원래 관측이 로컬 서버 빌드의 것이었고 캐시 헤더 차이로 로컬에서만 보였을 가능성이 큽니다.

다만 이 롤백이 반증한 것은 "중복 다운로드" 주장뿐입니다. "중복이 아니어도 부팅 창에서 3.0MB를 받는 것 자체가 파이프를 점유한다"는 별개의 주장은 아직 검증되지 않았습니다. 그리고 이 축은 로컬 서버 빌드로 판정할 수 없습니다 — 회선·기기 경합이 원인인데 개발 환경에는 그 조건이 없기 때문입니다.

9 — 2130_GAMEPLAY_FIRST_MATCH 발화율이 기대와 다르다 확인 필요

코드상 전체 유저 판당 1회로 설계됐는데, 실측은 솔리테어 RU에서 5.3%, NRU에서는 표본 임계(50) 미만이라 집계에 잡히지도 않았습니다.

이 로그는 2026-08-07에 추가됐으므로 측정 기간(08-08~10)에 해당 빌드가 아직 다 퍼지지 않았을 가능성이 큽니다. 다만 배선 오류일 가능성도 배제되지 않았습니다 — 빌드 버전별로 쪼개 확인해야 구분됩니다.
