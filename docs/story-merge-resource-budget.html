2. 로딩 타이밍 — 플로우 어디서 받고, 어디서 메모리에 올리는가

다운로드와 메모리는 별개다

bundle.preload() 는 바이트만 받아 캐시에 넣습니다 — 디코딩하지 않으므로 메모리를 거의 쓰지 않습니다. bundle.load() 가 디코딩과 에셋 생성을 하고, 여기서 메모리와 메인 스레드를 씁니다. 그래서 다운로드는 미리, 디코딩은 필요할 때가 됩니다. 60MB 예산은 load 된 것만 세면 됩니다.

"필요한 것만" 이 안전한 조건

온디맨드가 끊김으로 바뀌는 건 필요한 순간에 땡길 때입니다. 세 조건을 만족하면 대기가 사라집니다 — ① 언제 필요한지 데이터로 알 수 있고, ② 한 단계 앞서 받고, ③ 디코딩을 유휴 구간에 둘 것. 대화 캐릭터는 셋 다 만족합니다. 반대로 유저가 아무 때나 여는 영역은 ①이 깨지므로 게이트가 답입니다.

이전 800KB 는 FB Instant Games 권장을 옮겨 적은 자체 목표선이었고 실측 근거가 없었습니다. 2026-08-31 두 기준작의 build/fb-instant-games 를 gzip 기준으로 재서 목표선을 바꿨습니다 — 1차 코지타일 805KB(목표), 2차 솔리테어 1175KB(초과작이므로 상한). 공교롭게 1차 실측값이 기존 800KB 와 거의 같아, 값이 바뀐 게 아니라 근거가 생긴 것입니다. 변수는 스크립트 번들 하나입니다 — 엔진 250KB 는 두 기준작 차이가 5KB 인 고정비이고, 총량 차이 370KB 중 192KB 가 스크립트 번들에서 납니다. 메모리 60MB · 드로우콜 50 · 60fps 는 여전히 근거가 없습니다 — 기준작 런타임 프로파일 전까지 판정에 쓰지 않습니다.

막는 건 용량이 아니라 번들 경계입니다

부팅이 기다리는 씬 에셋은 83KB뿐입니다. 다만 이 값에는 엔진과 스크립트 번들이 빠져 있고, 그 둘이 기준작에서 초기 로드의 대부분(1차 686KB · 2차 883KB gz)을 차지합니다 — 실제 여유는 story-merge 를 한 번 빌드해 봐야 압니다. 지금 확실한 문제는 assets/bundle 이 번들 1개라는 것 — 지연 로딩 경계가 코드에만 있고 배포 단위에는 없습니다. 먼저 번들 3분할 + 미참조 66.8MB 정리, 그다음 1010_LOAD_COMPLETE 로 전후를 재면 됩니다.
