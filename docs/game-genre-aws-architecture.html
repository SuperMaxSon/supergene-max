게임 장르별 AWS 아키텍처 — 2024

메가존클라우드가 준 원본은 설명 한 줄 없는 구성도 4장입니다. 아이콘만 봐서는 장르별로 뭐가 달라지는지 안 보여서, 같은 그림을 다시 그리고 차이를 글로 붙였습니다. 핵심은 서비스 목록이 아니라 게임 서버가 상태를 갖느냐 하나입니다 — 그것 하나로 스케일 단위도, 진입 경로도, 비용 성격도 전부 갈립니다.

4장 모두에 똑같이 붙어 있는 것 — 그래서 아래 그림에서는 뺐습니다

Route 53(DNS) · CloudFront(CDN) · WAF + Shield Advanced(방어)가 모든 장르의 입구에 동일하게 있고, 데이터는 예외 없이 관계형(RDS 계열) + NoSQL/캐시 2계층입니다. 운영 도구(S3 · Secrets Manager · Certificate Manager · CloudWatch · CloudTrail · Systems Manager)도 4장에 똑같이 나열돼 있는데, 원본에는 선이 하나도 연결돼 있지 않습니다 — "쓰긴 쓴다"는 표시일 뿐 어디에 붙는지는 그림이 말해주지 않습니다. 공통분은 아래 4개 그림에서 생략했으니, 그림에 남은 것이 곧 장르별 차이입니다.

① 웹 기반 비동기 서버가 상태를 안 가짐 — 그래서 유일하게 자동 스케일이 성립합니다

우리(솔리테어 · 캐주얼)가 여기입니다

판이 요청 단위로 끝나고 서버가 특정 유저를 붙들고 있지 않으니, 아무 인스턴스나 받아도 됩니다. 그래서 ELB → Auto Scaling이 그대로 성립하고, 트래픽이 빠지면 인스턴스도 같이 줄어 비용이 트래픽에 비례합니다. 그림에서 "상시 서버"와 "서버리스"가 나란히 있는 것은 택일이 아니라 혼용 가능하다는 뜻입니다 — 상시 API는 컨테이너로, 이벤트성 작업은 Lambda로 나누는 구성을 한 장에 겹쳐 그린 것입니다.

② MMORPG 서버가 월드를 붙들고 있음 — 자동 스케일이 사라집니다

이 그림에 Auto Scaling이 없는 게 실수가 아닙니다

게임 서버가 특정 월드의 상태를 메모리에 들고 있어서 아무 서버나 붙을 수 없습니다. 유저는 "서버 1번"에 접속하는 것이지 로드밸런서 뒤 아무 데나 가는 게 아니고, 그래서 서버마다 고정 IP가 붙고 ELB를 못 씁니다. 늘리는 단위는 인스턴스가 아니라 월드(Realm) 통째 — 신규 서버 오픈이 곧 스케일아웃입니다. 대신 로그인·상점처럼 상태 없는 부분만 떼어 ELB 뒤 Private subnet에 두는데, 이게 ①의 구조와 정확히 같습니다. 실시간 트래픽이 ELB 대신 Global Accelerator로 들어가는 것도 같은 이유입니다.

③ 세션 기반 — 자체 구축 매치가 끝나면 상태도 끝남 — 상태의 수명이 "한 판"입니다

①과 ②를 반씩 섞은 구조입니다

게임 서버는 한 판 동안만 상태를 갖습니다. 그래서 ②처럼 플릿에 고정 IP를 붙여 직접 접속시키되, ①처럼 로비·로그인은 Auto Scaling으로 굴립니다. 자동으로 못 늘리는 대신 매치메이킹이 "빈 서버에 방을 꽂는" 역할을 하는 게 이 장르의 추가 부품입니다. 오른쪽 Region B는 DB까지 복제한 게 아니라 서버 플릿만 둔 것 — 멀리 있는 유저의 핑만 줄이고 데이터는 홈 리전 하나로 유지하는 방식입니다. 상단의 EventBridge · SQS · Lambda는 전투 결과 정산처럼 즉답이 필요 없는 일을 큐로 빼는 배관입니다.

④ 세션 기반 — GameLift + 서버리스 ③에서 직접 운영하던 부분을 통째로 AWS에 넘긴 버전

③과 비교하면 "무엇을 안 하게 되는지"가 이 그림의 내용입니다

직접 짜던 매치메이킹 · 서버 플릿 기동/회수 · 리전 배치가 GameLift 한 상자로 들어가고, 로비·결과·전투 로직은 Lambda로 바뀌어 상시 서버가 0대가 됩니다. ELB 자리는 API Gateway가 대신합니다. 대가는 GameLift 종속과 Lambda 특성(콜드 스타트, 실행 시간 상한)이라, 한 판이 길거나 서버가 계속 틱을 돌려야 하는 게임에는 안 맞습니다. 원본은 이 트레이드오프를 한 줄도 적어두지 않았습니다.

장르가 정해지면 1행(서버 상태)이 자동으로 정해지고, 나머지 6행은 거의 따라옵니다. 그래서 "우리는 ③이 좋을까 ④가 좋을까" 같은 질문은 1행이 같은 ③·④ 사이에서만 의미가 있습니다. ①과 ②는 고르는 대상이 아니라 게임 형태가 이미 결정한 결과입니다.

원본 문서의 한계 — 도입 판단에는 그대로 못 씁니다

4장 어디에도 규모 기준(DAU 몇부터 이 구성인지) · 비용 · 인스턴스 사양 · 장애 대응이 없습니다. 운영 도구 6종도 선 없이 나열만 돼 있어 어디에 붙는지 모릅니다. 실제 검토로 넘어가려면 우리 트래픽 수치를 넣은 견적을 따로 요청해야 합니다.

확인 범위 원본 PDF 4페이지를 전부 이미지로 렌더링해 아이콘·연결선·그룹 경계를 판독했습니다. 위 4개 그림은 원본을 옮겨 그린 것이며, 공통분(DNS · CDN · WAF · Shield · 운영 도구 6종)은 가독성을 위해 ① 외에는 생략했습니다. 추정 원본 아이콘 중 라벨이 없는 DB 4종은 정확한 서비스명을 특정할 수 없어 RDS 계열 · 캐시 · NoSQL로 뭉뚱그렸습니다(Aurora인지 RDS Multi-AZ인지, ElastiCache인지 MemoryDB인지 구분 불가). ③·④ 상단의 SQS도 아이콘 판독 기준 추정입니다. 원본 메가존클라우드_게임 장르별 아키텍처 자료.pdf (2024).
