먼저 손대야 하는 3가지 — 나머지 전부의 선행

① 셀 자료형 — 지금 셀은 number(레벨) 하나라 §L0 보드 코어가 요구하는 상태 필드를 담을 자리가 없습니다. Cell { itemId, charges, state } 로 바꾸는 게 IN-2 · IN-3 · IN-7 의 공통 선행입니다.

② 인게임↔아웃게임 계약 — 현재 계약은 showViewMergeBoard(node) → waitForCompletion(): Promise<boolean> 불리언 하나뿐이고, 버튼 콜백에서만 resolve 되어 다른 경로로 닫히면 영구 대기합니다. 에너지 소비 · 오더 제출 · 재화 획득 · 인벤토리 출납이 전부 이 경계를 지나갑니다.

③ 재화 원장 — 종류(코인 · 보석 · 에너지 · 경험치 · 패스포인트 · 이벤트재화)를 따로 만들면 상점 · 패스 · 이벤트가 붙을 때마다 지급 경로가 N×M이 됩니다. grant / spend(type, amount, reason) 단일 진입점 + 사유 태깅. reason 이 없으면 OUT-11 의 재화 흐름 계측이 불가능합니다.

현재 vs 포맷만 바꿨을 때

아트를 다시 그리는 얘기가 아닙니다

픽셀 수·구도·품질은 그대로 두고 저장 포맷만 바꾼 값입니다. 절감의 정체는 하나 — 알파가 없는 전체화면 그림을 PNG로 저장하고 있는 것. PNG는 사진성 이미지 압축을 못 해서 장당 1,505KB가 나오고, 같은 그림이 JPEG q85면 201KB입니다. PNG에 brotli는 안 먹습니다(−1.6% 실측) — 전송 압축으로는 해결되지 않습니다.

왜 이게 그대로 배포되나 — 1024 경계

이 그림이 결론입니다

720×1280 컷신·배경은 1024 상한을 넘어 아틀라스에 못 들어갑니다. 그래서 빌드가 손봐 주지 않고 소스가 그대로 나갑니다 — 전체 이미지의 63%가 이 경로입니다. 즉 이 프로젝트에서 포맷 결정은 아트 납품 단계에서 끝나야 합니다. 반대로 1024 이하 UI·아이템은 아틀라스가 통일해 주므로 손댈 필요가 적습니다.
