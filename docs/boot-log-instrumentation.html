부팅 소실 계측 추가

2026-09-01 빌드 480에서 FB SDK 대기 구간(1b)의 세션이 사라졌는데, 그 자리에 로그가 한 줄도 없어서 이탈인지 SDK 실패인지 그 밖의 무엇인지 끝까지 못 갈랐습니다. 이 문서는 그 부채를 갚는 계측의 최종안입니다 — 무엇을 넣는지, 무엇을 일부러 뺐는지, 그리고 이걸 다 넣어도 여전히 안 풀리는 것까지 적었습니다. 마지막 항목이 제일 중요합니다: 어제 우리를 속인 건 소실의 성격이 아니라 소실의 규모였습니다.

INTRO_FB_START는 있는데 INTRO_FB_START_FINISH가 없다 — 세 가지 원인이 전부 이 하나의 모습으로 나타납니다. 유저가 기다리다 나갔든, SDK가 reject했든, 페이지가 죽었든 구분이 안 됩니다. 그래서 조사에서 가설을 열세 개 세우고 하나씩 죽였지만 메커니즘은 끝내 특정하지 못했습니다. BigQuery로는 더 갈 수 없고, 클라이언트에 관측점을 심는 것 말고는 방법이 없습니다.

소실 3갈래 둘은 로그로, 하나는 잔차로

갈래 무슨 일 어떻게 잡히나 관측
SDK reject initializeAsync()가 실패로 끝남 INTRO_FB_START_FAIL + error_code · error_message 직접
이탈 기다리다 유저가 나감 INTRO_FB_ABANDON (pagehide → sendBeacon) 직접
미확인 로그가 남지 않아 성격을 특정할 수 없는 나머지 로그 없음 — 잔차로만 간접
셋째 갈래를 「사망」이라 부르면 안 되는 이유

처음에는 이걸 페이지 사망이라고 불렀는데, 정확하지 않았습니다. 잔차에는 성격이 다른 세 가지가 섞여 있습니다:

미확인 = START − FINISH − FAIL − ABANDON

잔차에 섞여 있는 것

① 진짜 사망 — 렌더러 크래시 · 메모리 부족. 프로세스가 죽어 JS가 안 돕니다. 다만 모바일에서 OS가 탭을 회수할 때는 pagehide가 뜨는 경우가 많아, 진짜 크래시의 상당수는 이미 ABANDON에 들어가 있습니다.

② 여전히 대기 중 — initializeAsync가 끝나지 않았고 유저도 나가지 않은 상태. 아무것도 죽지 않았고 탭은 살아 있습니다. 빌드 480에서 의심했던 시나리오가 정확히 이것입니다 — 엔진 실행이 메인 스레드를 오래 물면 .then() 콜백이 밀립니다.

③ 계측 실패 — FAIL·ABANDON이 서버에 도달하지 못한 경우. 소실이 아니라 우리 로그가 유실된 것입니다.

그래서 이 숫자는 사망 건수가 아니라 상한이자 혼합입니다. 「미확인」으로 부르는 게 맞습니다 — 「사망」은 우리가 모르는 것을 안다고 말하는 이름이었습니다.

정상 세션은 로그가 한 줄도 안 는다

이벤트 3종은 전부 실패 시에만 발생하고, 필드 4개는 기존 로그에 칸만 붙습니다. 부팅 경로에 XHR을 추가로 발생시키지 않는다는 게 이 설계의 핵심입니다 — 1b는 우리가 측정하려는 구간이라, 그 안에서 로그를 더 쏘면 관측 도구가 관측 대상을 느리게 만듭니다.

.catch 대신 then(onOk, onFail)을 쓴 이유

.catch를 별도 체인으로 붙이면 .then(onOk)이 만든 파생 promise가 reject된 채 방치돼 unhandledrejection이 뜹니다(콘솔 에러 + Sentry 노이즈). 두 인자 형태는 그걸 막고, 동시에 onOk 내부 예외가 FAIL로 오분류되는 것도 막습니다.

뺀 것 한 번 넣었다가 되돌린 4종

뺀 항목 왜 뺐나 잃는 것
INTRO_FB_START_SLOW_1S / 3S / 5S 직전 빌드 RU p50이 5.32초 — 5초 워치독조차 정상 세션 절반이 쏜다. 게다가 그 XHR이 측정 대상인 1b 창 안에서 initializeAsync와 네트워크를 경쟁한다 미확인 세션이 몇 초에서 멎었는지 모름
INTRO_FB_HIDDEN iOS Safari는 백그라운드 전환에 pagehide가 뜨는 경우가 많아 ABANDON과 중복 발화한다. 플래그가 따로라 서로 막지도 않는다 미확인을 백그라운드 / 포그라운드로 못 나눔
"오래 걸려서 나간 경우"는 이미 잡힌다

워치독의 원래 목적이 실패는 아닌데 오래 걸려 이탈하는 케이스였는데, 그건 INTRO_FB_ABANDON이 잡습니다. 그리고 거기 실린 data.time은 ms 단위라, 5초·10초 두 칸으로 뭉갠 워치독보다 정밀합니다. 워치독이 유일하게 값을 갖는 건 로그가 아예 없는 미확인 케이스뿐인데, 그 하나 때문에 전 세션 볼륨을 두 배로 만드는 건 맞지 않습니다.

부수 효과로 타이머 3개와 리스너 1개가 사라져 부팅 크리티컬 패스가 단순해졌습니다. 계측이 부팅 경로에 있다는 게 이 작업의 가장 큰 리스크였습니다.

팀 제안 대조 독립적으로 나온 4건과의 비교

제안 현재 상태 비고
① 초기화 실패 로그 구현됨 INTRO_FB_START_FAIL. 다만 .catch가 아니라 then(onOk, onFail)
② 지연 감시 (5초 · 10초) 제외 §뺀 것 참조 — ABANDON+time과 중복, 볼륨 과다
③ 세션 구분 번호 구현됨 data.sid. 제안한 4개 이벤트를 포함해 모든 부팅 로그에 실림

제안서가 인용한 main.js 줄 번호는 계측 패치 이전 기준입니다. 패치가 아직 미커밋이라 그렇습니다. 중복 작업이 나기 전에 맞춰야 합니다.

남은 구멍 이걸 다 넣어도 안 풀리는 것

어제 우릴 속인 건 소실의 성격이 아니라 규모였다

사고 후 확인 결과 한 사람이 20건 넘게 만들었습니다. 그러면 그동안 못 풀던 것이 한꺼번에 설명됩니다 — isNewDevice는 localStorage 유무로 정해지므로 같은 사람이 재시도하면 첫 회만 NRU, 이후는 전부 RU가 됩니다. RU 편중도, 45분이라는 짧은 창도, 미국 단독도, 롤백 전에 이미 회복된 것도 전부 여기서 나옵니다.

계측을 다 넣고 어제로 돌아가도 결과는 이렇습니다 — "이탈이 많았다"는 답은 나오지만, 그게 한 사람인지 24명인지는 여전히 모릅니다. sid는 페이지 로드마다 새로 나므로 재시도 20번은 무관한 20건입니다.

제안 — 필드 두 개

did (localStorage 영구 랜덤 id) 와 attempt (부팅마다 +1). 이벤트가 아니라 필드라 볼륨 비용이 0이고, 통과율을 사람 기준으로 재계산할 수 있게 됩니다. attempt=20이 로그에 직접 보이므로 재시도 루프 자체가 관측 대상이 됩니다.

한계 — localStorage 삭제 · 시크릿 모드 · 기기 교체에는 무력합니다. 그리고 소급되지 않습니다. 그래서 이건 아래 방어선을 대체하지 못하고 보강만 합니다.

배포 후 확인 순서 순서가 중요하다

# 확인 왜 이 순서인가
1 INTRO_FB_ABANDON 건수 > 0 가장 먼저. sendBeacon이 서버에 거부되면 0건이 나오는데, 그건 "이탈 없음"과 구분되지 않습니다. 0이면 잔차식 전체가 무의미해집니다
2 FIRST_LOG에 sid · time · device가 실리는지 필드 주입이 실제로 되는지 확인. 여기가 비면 이후 분석 축이 전부 없습니다
3 log_build_error 건수 0이 정상. 값이 있으면 로그 조립이 실제로 던지고 있다는 직접 증거
4 FAIL / ABANDON 비율과 미확인 잔차 이게 정상 빌드의 기준선이 됩니다. 다음 사고 때 비교 대상
5 3D 모듈 재투입 기준선을 확보한 뒤. 트래픽이 적은 시간대에
연관 문서 솔리테어 부팅 로그 플로우 — 로그가 찍히는 순서와 구간

확인 범위 main.js 계측 패치는 미커밋 상태입니다. p50 5.32초 · 통과율 99.19% → 80.17% · 하류 89.69% vs 89.36%는 사고 조사 시점의 BigQuery 실측값입니다. "한 사람이 20건 이상"은 별도 확인된 값이며, 식별에 사용한 축은 이 문서에 반영되지 않았습니다.
