이 문서만 읽고 답할 수 있게 만들었다. 아래 32개 행은 개발 기획서와 서버 프로토콜이 같은 기능을 다르게 적었던 곳이다. 행마다 지금 기획서 문장과 지금 프로토콜 문장을 나란히 적었다. 프로토콜 원문은 서버 레포에만 있으므로 프로토콜 칸을 원문 요약으로 믿어도 된다(S:줄 = merge-story-server origin/main 1170a96 src/model/type-protocol.ts 줄 번호). 「추론」이 붙은 문장은 원문이 아니라 원문에서 끌어낸 판단이다.

상태

  • 결정 반영 (29건): 기획서에 결정이 들어가 두 문서가 같은 규칙을 적는다. 기획서 칸에 절 · 앵커 · 판본을 적었다. 답하지 않는다.
  • 열림 (3건): EV-01 · EV-09 · SH-02. 아래 할 일.

결정 반영 행의 노란 글씨는 결정과 맞지 않는 옛 문구나 경로 이름이 기획서 다른 곳에 남은 자리, 또는 그 뒤 프로토콜에만 더해진 내용이다. 규칙 결정은 끝났고 문구 정리만 남았다.

할 일 — 열림 3건만 어느 쪽으로 맞출지 정한다. 기획서 원문을 확인할 수 있으면 해당 절을 열어 근거를 붙인다.

  • 기획서: 기획서가 맞다 → 서버 프로토콜을 기획서대로 고친다
  • 프로토콜: 프로토콜이 맞다 → 기획서를 프로토콜대로 고친다
  • 둘 다 수정: 둘 다 아니다 → 새 규칙을 적는다
  • 보류: 지금 정할 수 없다 → 누가 · 무엇을 정해야 하는지 적는다
  • EV-01 향초 품평회 완주 뒤 — 동작은 두 문서가 같다(완주 뒤 난이도 재선택 · 1단계부터 · 횟수 제한 없음). 기획서 6.3.1에만 「현재 서버 프로토콜은 회차 최초 참가 때만 난이도를 받고 … 서버 프로토콜에 먼저 반영해야 한다」는 미반영 문단이 남아 있다. 이 문단을 닫아도 되는지 정한다.
  • EV-09 수집 앨범 · 개인 마일스톤 — 기획서는 앨범 진행 상태와 서버 API(팩 개봉 · 세트 보상 · 교환 상자)를 D29 전에 서버에 추가해야 한다고 적었고, 프로토콜은 앨범 · 마일스톤을 런칭 범위 밖(시트 행만)으로 둔다. 서버 추가 시점과 담당을 정한다.
  • SH-02 광고 한도 초과 응답 — 기획서는 RATE_LIMITED를 따로 내라고 적었고, 프로토콜은 TABLE_UPDATE_REQUIRED를 내며 RATE_LIMITED 코드가 없다. 어느 쪽으로 맞출지 정한다.

원칙 — 기획서에 결정 기록(확정일 · 결정자 · Slack 번호)이 있으면 그걸 근거로 쓴다. 결정 기록이 없으면 기획서 원문 문장을 근거로 써도 되지만, 근거 칸에 「결정 기록 없음」을 함께 적는다. 근거가 전혀 없으면 추측하지 말고 보류로 답한다.

참고 — 개발 기획서는 매우 커서 일부 웹 읽기 도구는 본문을 다 받지 못한다. 원문이 필요하면 HTML을 그대로 받아 앵커(예: #dp-bot-race)나 절 번호(예: 6.3.1)로 찾는다. 결정 반영 내역은 버전 히스토리 v1.24 「서버 프로토콜 차이 32건 결정 반영」(#build-note-v1-24)에 있다.
