게임 전체 공유층 한 벌 + 뷰 두 축

밸런스 시트 59탭 중 20탭만 로더에 등록돼 있다 — 아웃게임 데이터(main_task · daily_task · area_unlock · skin_deco · unlock · album_*)는 시트에 있고 코드가 안 읽는다
이 그림을 읽는 법

가로 세 덩어리가 공유층 · 인게임 · 아웃게임입니다. 공유층은 뷰가 바뀌어도 살아 있는 층이라 위에 따로 뺐고, 아래 두 축은 같은 5층(view · pooled+popup · vm · rules · data)을 각각 한 벌씩 가집니다. 인게임 쪽은 실선, 아웃게임 쪽은 점선입니다 — 점선은 정본 기획에는 있고 코드가 0줄인 칸입니다. 주황은 이번에 들어온 층(PlayerVM · IngameVM)이고, 인게임에서 아직 남은 건 맨 위 view 가 이 VM 을 읽게 하는 배선뿐입니다.

아웃게임 정본 5장 · 코드 0줄

아웃게임은 인게임과 같은 5층을 그대로 한 벌 더 세우게 된다 — 공유층만 겹친다
왜 이 그림이 비어 보이나

화면 58(마을 홈)을 뿌리로 두고 여는 지면 4장을 내린 것입니다. 전부 점선인 이유는 정본 화면 기획서에는 확정돼 있는데 클라이언트 코드가 아직 한 줄도 없기 때문입니다. 현재 코드에 존재하는 아웃게임 진입점은 onClickOutgame() 안의 CClog("not implemented yet") 한 줄입니다. 규모(꾸미기 자리 130 · chore 188건 · Day 20)를 같이 적은 건 이 축이 인게임의 곁가지가 아니라 인게임과 대등한 한 벌이라는 판단 근거이기 때문입니다.

인게임 완성형 1~12단계를 끝냈을 때의 목표

가운데 층이 들어왔다 — 남은 건 view 가 VM 을 읽게 하는 배선과 아웃게임 한 벌이다
완성형과 현재의 차이

위에서 아래로 view → vm → rules → data, 올라오는 화살표는 이벤트(bus.emit(scope))입니다. rules 층은 순수 계산이라 cc 참조가 0건이고 Math.random 도 없습니다 — 무작위는 PickFn 으로 주입받기 때문에 Node 러너 16종 608 PASS 가 엔진 없이 돌아갑니다. 프리팹 24종과 풀 premake 120은 이미 다 있고, 팝업 10종 중 호출부가 연결된 건 2종뿐이라 남은 일이 '만들기'가 아니라 '잇기'로 갈립니다.

12단계가 여는 것 구간마다 무엇이 열리는가

초록 = 로직 완료 · 남은 건 ingame/view/ 배선. 5~11의 판정은 전부 VM 에 들어와 있다
순서를 이렇게 잡은 이유

가로 12칸이 작업 단계고, 아래 띠가 그 구간을 끝내면 플레이어에게 무엇이 열리는지입니다. PlayerVM + 저장 2키를 1번으로 끌어올린 게 이 순서의 핵심입니다 — 계정 상태와 세션 상태를 먼저 갈라 두면 헤더가 뷰 전환과 무관해지고, 나중에 아웃게임이 같은 층을 그대로 씁니다. 나중에 가르면 이미 붙은 화면을 다 뜯어야 합니다. 초록은 판정 로직이 이미 VM 에 들어온 단계이고, 남은 건 ingame/view/ 배선입니다.

한 사이클 터치 → 판정 → 상태 → 렌더

판정(xxxCheckAt)과 적용(xxx)이 2메서드로 갈려 있다 — 확인 팝업을 취소해도 되돌릴 게 없다
판정과 적용을 왜 갈랐나

xxxCheckAt()(판정)과 xxx()(적용)이 서로 다른 메서드로 갈려 있습니다. 판정은 상태를 건드리지 않으므로 확인 팝업을 띄웠다가 취소해도 되돌릴 게 없습니다 — 되돌리기 스택이 필요 없어지는 지점입니다. 저장은 매 머지마다 하지 않고 markDirty() 로 표시만 해 두고 tick 에서 0.5초에 한 번 flush 합니다. 동기 localStorage 쓰기가 머지마다 들어가면 프레임이 떨어지기 때문입니다. 타이머도 VM 이 들지 않습니다 — rules/vm 은 cc 가 없는 층이라 schedule 자체가 없고, View.update(dt) → VM.tick(dt) 로 시간만 흘려 넣습니다.

상태를 어디가 소유하나 나가도 살아 있어야 하는가

이 분리가 코드에 들어갔다 — PlayerVM 은 reset() 이 아예 없고, IngameVM 만 세션마다 접힌다
이 분리가 지키는 것

판단 기준은 한 줄입니다. 인게임을 나가도 살아 있어야 하면 PlayerVM, 아니면 IngameVM. 그래서 PlayerVM 에는 reset() 이 아예 없고, IngameVM 만 onHideStart() 에서 접힙니다. 헤더 · 상점 · 앨범 · 아웃게임은 PlayerVM 하나만 구독하면 되므로 뷰 전환과 무관해집니다. 참조는 IngameVM → PlayerVM 단방향이라 역방향 의존이 생기지 않습니다.

오더 한 장 양 끝만 있고 가운데가 빈다

랜덤 추첨 8단계는 별건으로 남아 있다 — 지금은 order_fixed 16행 순번만 돈다
'양 끝만 있다'의 뜻

왼쪽(시트 8탭 · 판정 OrderRules)과 오른쪽(프리팹 · 풀 8/16 · 납품 팝업)이 둘 다 준비돼 있는데 가운데 레일 뷰만 빈 노드(railRoot)라서 화면에 아무것도 안 뜹니다. 남은 작업이 한 칸이라는 뜻입니다. 지금 편성은 order_fixed 16행을 순번으로 도는 고정 편성이고, 랜덤 추첨 8단계는 별건으로 남습니다. 요구 칸은 2개 고정이며 중복 코드가 허용됩니다 — 시트가 2칸을 다 안 채운 행이 있어도 상수 쪽을 지우면 안 되는 이유입니다. 보상은 A(코인)만 데이터가 있고 B · C 열은 아직 비어 있습니다.

확인 범위 story-merge-proto-client main 브랜치 2026-09-16 작업 트리 실측입니다. 줄 수는 assets/script/game/ingame/ 하위 .ts 기준이고, PASS 수치는 Node 러너 16종을 그날 돌린 결과입니다. 아웃게임 화면 번호(58 · 81 · 78 · 61 · 32)와 규모 수치는 정본 화면 기획서 4.5절에서 가져왔습니다 — 코드 실측이 아니라 기획 확정값입니다. 도식 02 는 현재 상태가 아니라 1~12단계를 끝냈을 때의 목표 구조입니다.
