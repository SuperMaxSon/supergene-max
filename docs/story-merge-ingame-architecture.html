게임 전체 공유층 한 벌 + 뷰 두 축

밸런스 시트 46탭 중 인게임 20탭만 export 돼 번들에 실려 있고, 로더는 그 20탭을 전부 읽는다 — 아웃게임 데이터(main_task · daily_task · area_unlock · skin_deco · album_*)는 export 대상 밖이라 코드가 볼 수조차 없다
이 그림을 읽는 법

가로 세 덩어리가 공유층 · 인게임 · 아웃게임입니다. 공유층은 뷰가 바뀌어도 살아 있는 층이라 위에 따로 뺐고, 아래 두 축은 같은 5층(view · pooled+popup · vm · rules · data)을 각각 한 벌씩 가집니다. 인게임 쪽은 실선, 아웃게임 쪽은 점선입니다 — 점선은 정본 기획에는 있고 코드가 0줄인 칸입니다. 주황은 뒤늦게 들어온 층(PlayerVM · IngameVM)입니다. 인게임 쪽은 그 뒤로 보드 입력과 오더 레일까지 붙어 view 가 실제로 VM 을 읽고 있고, 남은 건 연출·실패 UX 마감입니다. 스토리 태스크 칸이 점선인 건 레거시 2종(PopupTask · ViewMergeBoard 42칸)을 2026-09-16 에 지웠기 때문입니다 — 아웃게임 기획이 없어 완료 조건을 정의할 수 없으므로 태스크 노드는 지금 자동 완료로 넘깁니다.

아웃게임 정본 5장 · 코드 0줄

아웃게임은 인게임과 같은 5층을 그대로 한 벌 더 세우게 된다 — 공유층만 겹친다
왜 이 그림이 비어 보이나

화면 58(마을 홈)을 뿌리로 두고 여는 지면 4장을 내린 것입니다. 전부 점선인 이유는 정본 화면 기획서에는 확정돼 있는데 클라이언트 코드가 아직 한 줄도 없기 때문입니다. 현재 코드에 존재하는 아웃게임 진입점은 여전히 onClickOutgame() 안의 CClog("not implemented yet") 한 줄입니다 — 인게임이 5,229줄에서 9,220줄로 크는 동안 이 축은 0줄 그대로입니다. 규모(꾸미기 자리 130 · chore 188건 · Day 20)를 같이 적은 건 이 축이 인게임의 곁가지가 아니라 인게임과 대등한 한 벌이라는 판단 근거이기 때문입니다.

인게임 완성형 목표 구조 · 지금 어디까지 찼나

가운데 층과 보드·레일 배선이 들어왔다 — 남은 건 연출·실패 UX 마감과 아웃게임 한 벌이다
완성형과 현재의 차이

위에서 아래로 view → vm → rules → data, 올라오는 화살표는 이벤트(bus.emit(scope))입니다. rules 층은 순수 계산이라 cc 참조가 0건이고 Math.random 도 없습니다 — 무작위는 PickFn 으로 주입받기 때문에 Node 러너 15종 816 PASS 가 엔진 없이 돌아갑니다. 주황 두 칸(OrderDraw 876줄 · OrderRng 113줄)이 이번에 들어온 추첨 경로이고, rules 는 6종 1,415줄에서 8종 2,541줄로 커졌습니다. 프리팹은 22종(레거시 3종 삭제), 풀 premake 128입니다. 팝업 9종 중 호출부가 연결된 건 여전히 2종뿐이고, MergeFxNode·RailCardNode 도 풀만 있고 TS 호출부가 0이라 주황으로 뒀습니다. 오른쪽 주황 점선은 계획대로면 이미 했어야 할 분할입니다 — 판정이 다 들어오면서 IngameVM 이 1,384줄이 됐는데 기준으로 잡은 600줄에서 BoardOps·OrderOps 로 빼는 작업이 아직 안 됐습니다. 팝업도 «호출부 2종»이 끝이 아닙니다 — PopupInventory 는 열리기는 하지만 InventoryModel 이 안 붙어 슬롯이 빈 채로 뜹니다.

12단계가 여는 것 지금 12번 «마감»에 서 있다

초록 = 끝난 단계. 1~11이 닫혔고 12(마감)만 남았다 — 토스트·플로팅 문구는 배선됐고 병합 연출(MergeFxNode)만 호출부가 없다
순서를 이렇게 잡은 이유

가로 12칸이 작업 단계고, 아래 띠가 그 구간을 끝내면 플레이어에게 무엇이 열리는지입니다. PlayerVM 과 계정·세션 저장 분리를 1번으로 끌어올린 게 이 순서의 핵심입니다 — 먼저 갈라 두면 헤더가 뷰 전환과 무관해지고, 나중에 아웃게임이 같은 층을 그대로 씁니다. 나중에 가르면 이미 붙은 화면을 다 뜯어야 합니다. 직전 판본에서 11번(오더)이 «지금 하려는 지점»이었고, 지금은 그게 닫혀 12번 «마감»에 서 있습니다 — 토스트(ToastNode)와 셀 위 문구(FloatingLabelNode)는 배선이 끝났고, 병합 연출 MergeFxNode 만 아직 호출부가 0입니다. 다만 1~4 구간의 «더미 사라짐»은 아직 완전하지 않습니다 — 지갑·레벨·에너지 잔량은 PlayerVM 실값을 읽지만, 에너지 구매 가격(DUMMY_ENERGY_PRICE_GEMS = 10)과 손님 초상(OrderAvatarLoader 폴백 4장)은 여전히 더미입니다. 소유권(EnergyModel·product 계단)과 아트 경로가 안 정해져서 남은 자리입니다.

한 사이클 터치 → 판정 → 상태 → 렌더

판정(xxxCheckAt)과 적용(xxx)이 2메서드로 갈려 있다 — 확인 팝업을 취소해도 되돌릴 게 없다
판정과 적용을 왜 갈랐나

xxxCheckAt()(판정)과 xxx()(적용)이 서로 다른 메서드로 갈려 있습니다. 판정은 상태를 건드리지 않으므로 확인 팝업을 띄웠다가 취소해도 되돌릴 게 없습니다 — 되돌리기 스택이 필요 없어지는 지점입니다. 저장은 매 머지마다 하지 않고 markDirty() 로 표시만 해 두고 tick 에서 0.5초에 한 번 flush 합니다. 동기 localStorage 쓰기가 머지마다 들어가면 프레임이 떨어지기 때문입니다. 타이머도 VM 이 들지 않습니다 — rules/vm 은 cc 가 없는 층이라 schedule 자체가 없고, ViewIngame.update(dt) 가 IngameVM.tick() 과 PlayerVM.tick() 을 직접 밉니다.

상태를 어디가 소유하나 나가도 살아 있어야 하는가

이 분리가 코드에 들어갔다 — PlayerVM 은 reset() 이 아예 없고, IngameVM 만 세션마다 접힌다. 저장 키도 축을 따라 갈렸다: playerState(계정) · boardState(세션) · orderGenState(발급 난수)
이 분리가 지키는 것

판단 기준은 한 줄입니다. 인게임을 나가도 살아 있어야 하면 PlayerVM, 아니면 IngameVM. 그래서 PlayerVM 에는 reset() 이 아예 없고, IngameVM 만 onHideStart() 에서 접힙니다. 헤더 · 상점 · 앨범 · 아웃게임은 PlayerVM 하나만 구독하면 되므로 뷰 전환과 무관해집니다. 참조는 IngameVM → PlayerVM 단방향이라 역방향 의존이 생기지 않습니다. 저장 키도 이 축을 그대로 따릅니다 — 계정 playerState, 세션 boardState, 그리고 오더 추첨이 들어오면서 난수 상태를 담는 orderGenState 가 세 번째 키로 붙었습니다. 난수기를 새로 만들면 같은 카드가 다시 나오므로 세이브와 한 몸이어야 하기 때문입니다.

오더 한 장 가운데 두 칸이 이어졌다

고정(order_fixed 16행)이 먼저, 빈 자리는 8단계 추첨이 채운다 — 난수기는 세이브와 한 몸이라 orderGenState 가 세 번째 저장 키로 생겼다
'양 끝만 있다'의 뜻

직전 판본에서 가운데 두 칸(추첨 · 레일 뷰)이 비어 있던 구간이 이어졌습니다. OrderDraw 876줄이 정본 8단계 추첨을 옮겼고 — 단계마다 export 하는 건 카드가 깨졌을 때 8단계 중 어디서 갈렸는지 러너가 짚을 수 있게 하려는 것입니다 — OrderRailNode 177줄이 railRoot 를 채웁니다. 납품 팝업은 만들지 않고 지웠습니다: PopupOrderServe 를 삭제하고 레일 카드 탭에서 바로 serveCheckAt → serveOrder 로 갑니다. 요구 칸은 2개 고정에 중복 코드 허용이고 — 시트가 2칸을 다 안 채운 행이 있어도 상수 쪽을 지우면 안 되는 이유입니다 — 보상은 order_price 합(코인) + diff_score 이며 경험치는 0(ORDER_EXP_REWARD)입니다. RailCardNode 는 프리팹에 배치돼 있고 풀에도 올라와 있지만 TS 호출부가 0이라, 레일이 실제로 꺼내 쓰는 건 OrderCardNode 쪽입니다.
