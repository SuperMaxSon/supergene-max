솔리테어 바이럴 개편 전후 — 구간 대조

바이럴 개편을 구간 4개(개편 전 · 1차 · 2차 · 3차)로 끊고, DAU당 지표 10개를 같은 자에 나란히 놓았습니다. 값은 일별 평균이 아니라 구간 통산(합산 분자 ÷ 합산 분모)이고, 🎯 목표선은 마종·퍼블마 최근 3일 합산입니다. 막대에 마우스를 올리면 그 값의 모수가 나옵니다. 에스더 41번 관측 페이지의 같은 섹션을 허브로 옮긴 것이며, 수치는 BigQuery에서 받아 채웁니다.

솔리테어 BigQuery 목표선 = 마종 · 퍼블마 기준일 —

구간 대조 DAU당 10행 · 구간 통산 · 계열별 공유 스케일

읽는 법 왜 이렇게 봐야 하는지

막대 길이는 계열 안에서만 비교한다

스케일은 행마다 자기 최대로 늘리지 않고 같은 단위 계열끼리 공유합니다 (판수·광고 / 메세지·피드 / 토너 발화 3종 / 비율 3종). 행마다 늘리면 막대가 다 꽉 차서 계열 간 크기 차이가 사라집니다. 반대로 계열이 다른 행끼리는 길이 비교가 불가합니다 — 그때는 숫자와 Δ만 보세요.

「정의 상이」 배지가 붙은 4행은 개편 전과 축이 다르다

8/7에 로그 정의와 발화 정책이 바뀌었습니다(호출 시점 변경 · 거절 3회 캡 · 3110이 서버 등록 완료만으로 좁아짐). 그래서 이 행들의 개편 전 막대는 옅게(참고만) 그리고, Δ는 1차 대비로 잡습니다. 초대 2행은 2차(#450) 신설이라 개편 전·1차가 "없던 기능"으로 비어 있습니다.

목표선은 마종, 초대만 퍼블마 — 창은 최근 3일

활동성 2행(판수 · 총광고)은 마종의 부스팅 이후 창, 바이럴·비율 6행은 마종 동기간, 초대 2행은 마종에 없는 지면이라 퍼블마를 씁니다. 원본은 각 창을 5일 합산으로 봤지만 이 페이지는 프로젝트당 최근 3일 합산입니다 — 창이 짧아 일 변동에 민감하니 목표선은 눈금이지 합격선이 아닙니다.

구간 경계와 제외일

배포가 하루 안에 섞이는 8/7 · 8/13 · 8/18은 제외했습니다. 그래서 구간별 일수가 6 / 5 / 4 / … 로 불연속입니다. 3차만 오늘 부분일을 포함하며, DAU 믹스는 구간마다 다릅니다 (8/14~ 인게임 메뉴 신규 유입) — 판수 해석은 루커 표의 RU 행과 교차 확인이 필요합니다.

지금은 골격만 — 수치가 비어 있다

이 환경에 bq CLI가 없어 값을 직접 뽑지 못했습니다. 아래 #sql의 쿼리를 돌려 결과를 주면 페이지 하단 DATA 블록만 교체합니다. 그때까지 모든 행은 —로 그려집니다. 광고 완료의 rv_*와 초대 3단 inv_*은 이벤트 코드가 아직 미확정이라 0번 탐색 쿼리로 먼저 못박아야 합니다.

갱신 쿼리 이 세 개를 돌려 DATA 블록을 채운다

0. 탐색 — 광고·초대 이벤트 코드 확정 (최초 1회) 
-- rv_* (동영상 광고 완료)와 inv_* (초대 시도/성공/유입)의 이벤트 코드가 아직 미확정이다.
-- 클라 LogManager에는 4200_RV_START/4210_RV_FINISH와 4100/4110_INTERSTITIAL_RV_*가 함께 있고,
-- 초대는 2097_PRE_LEVEL_INVITE · 5207_BTN_LEADERBOARD_FRIENDS_INVITE · 11001_TOSS_INVITE_FRIEND_INFO가
-- 흩어져 있어 try/ok/유입 3단이 특정되지 않는다. 실제 발화량으로 먼저 고른다.
select event, count(*) c, count(distinct player_id) u
from `game-log-359704.raw.solitaire_city_journey`
where log_date between '2026-08-19' and '2026-09-02'
  and is_dev is distinct from true and player_id > 0
  and (event like '4%' or lower(event) like '%invite%' or lower(event) like '%toss%')
group by 1 order by 2 desc

결과로 매핑을 확정한 뒤 아래 1·2번 쿼리의 <RV_FIN> · <INV_TRY> · <INV_IN>을 치환합니다. 벤치 테이블(마종 · 퍼블마)이 같은 코드 체계인지도 미확인이라, 2번이 0으로 나오면 이 쿼리를 해당 테이블에 다시 돌려 맞춥니다.

1. 솔리테어 구간 집계 — 구간 4개를 한 번에 
-- DAU(ud)는 세션이 아니라 "1000_LOGIN_COMPLETE가 있는 (날짜, 플레이어) 쌍"이다.
-- 로그인 없는 날의 이벤트만 있는 행을 DAU로 세면 분모가 부푼다.
-- 배포가 섞이는 8/7 · 8/13 · 8/18은 구간에서 뺀다.
select case
    when log_date between '2026-08-01' and '2026-08-06' then 'e1'
    when log_date between '2026-08-08' and '2026-08-12' then 'e2'
    when log_date between '2026-08-14' and '2026-08-17' then 'e3'
    when log_date between '2026-08-19' and '2026-09-02' then 'e4' end era,
  count(distinct log_date) days,
  count(distinct if(has_login=1, format('%t|%t', log_date, player_id), null)) ud,
  countif(event='2300_GAMEPLAY_FINISH') fin,
  countif(event='<RV_FIN>') rv_fin,
  countif(event='4010_INTERSTITIAL_AD_FINISH') it_fin,
  countif(event='3410_MSG_P2P_SUCCESS') msg_ok,
  countif(event='3510_FEED_SHARE_SUCCESS') feed_ok,
  countif(event='3100_TOURNAMENT_CREATE') cr_try,
  countif(event='3110_TOURNAMENT_CREATE_SUCCESS') cr_ok,
  countif(event='3200_TOURNAMENT_SHARE') sh_try,
  countif(event='3210_TOURNAMENT_SHARE_SUCCESS') sh_ok,
  countif(event='<INV_TRY>') inv_try,
  countif(event='<INV_IN>')  inv_in
from (
  select log_date, player_id, event,
    max(if(event='1000_LOGIN_COMPLETE',1,0)) over(partition by log_date, player_id) has_login
  from `game-log-359704.raw.solitaire_city_journey`
  where log_date between '2026-08-01' and '2026-09-02'
    and is_dev is distinct from true and player_id > 0
)
where log_date not in ('2026-08-07','2026-08-13','2026-08-18')
group by era having era is not null order by era
2. 벤치 목표선 — 프로젝트별 최근 3일 (마종 2회 · 퍼블마 1회) 
-- 세 번 돌린다: 마종 활동성 창(부스팅 이후 D+33~35) → bench3.mahjong_pu
--               마종 동기간 창(D+48~50)            → bench3.mahjong
--               퍼블마 초대 창(최근 3일)            → bench3.pubma
-- 「최근 3일」은 캘린더 최근이 아니라 각 D+n 창의 마지막 3일이다 — 같은 D+n 대조라는 원래 의도를 유지한다.
select count(distinct log_date) days,
  count(distinct if(has_login=1, format('%t|%t', log_date, player_id), null)) ud,
  countif(event='2300_GAMEPLAY_FINISH') fin,
  countif(event='<RV_FIN>') rv_fin,
  countif(event='4010_INTERSTITIAL_AD_FINISH') it_fin,
  countif(event='3410_MSG_P2P_SUCCESS') msg_ok,
  countif(event='3510_FEED_SHARE_SUCCESS') feed_ok,
  countif(event='3100_TOURNAMENT_CREATE') cr_try,
  countif(event='3110_TOURNAMENT_CREATE_SUCCESS') cr_ok,
  countif(event='3200_TOURNAMENT_SHARE') sh_try,
  countif(event='3210_TOURNAMENT_SHARE_SUCCESS') sh_ok,
  countif(event='<INV_TRY>') inv_try,
  countif(event='<INV_IN>')  inv_in
from (
  select log_date, player_id, event,
    max(if(event='1000_LOGIN_COMPLETE',1,0)) over(partition by log_date, player_id) has_login
  from `game-log-359704.raw.<mahjong|puzzle_block_master>`
  where log_date between '<창시작>' and '<창끝>'
    and is_dev is distinct from true and player_id > 0
)
실행 방법

bq query --nouse_legacy_sql --max_rows=100000으로 돌립니다. --max_rows를 빼면 100행에서 잘립니다. 공통 필터는 is_dev is distinct from true and player_id > 0입니다.

확인 범위 이벤트 매핑은 assets/script/common/log/SolitaireTripeaksLogManager.ts 실측이고, rv_*·inv_* 2건은 미확정(0번 탐색 쿼리 대기)입니다. 구간 경계·제외일·목표선 규약은 원본 관측 페이지(에스더 41번)에서 그대로 가져왔습니다. 서구권(GEO) 분리와 UA/오가닉 분리는 이 페이지 범위 밖입니다 — 데이터에 org/ua 계층이 들어오면 유입 토글이 자동으로 나타납니다.
