벤치 3사 — 같은 3일치 코지 · 마종 · 퍼블마 · DAU당

차트의 목표선은 마종 하나뿐이라 이 표를 함께 본다

막대 차트는 행마다 목표선을 한 줄만 그릴 수 있어 원본 규약대로 마종(초대는 퍼블마)을 얹었습니다. 하지만 판정이 갈릴 때 실제로 먼저 보는 건 코지이므로, 세 벤치를 같은 창으로 나란히 둔 표를 따로 실었습니다. 마종은 DAU가 압도적으로 커서 단독 비교가 함정이 될 수 있습니다.

초대 2행은 퍼블마만 값이 있다

토너 초대 지면(3460_MSG_P2P_INVITE · position=tournament_invite)은 마종·코지에 없어 0입니다. 초대 유입률의 목표선은 아직 비어 있습니다 — 유입 세션은 이벤트가 아니라 entrypoint_now.entry로 세야 하는데, 어느 entry 값이 초대 유입인지 확정되지 않았습니다.

읽는 법 왜 이렇게 봐야 하는지

막대 길이는 계열 안에서만 비교한다

스케일은 행마다 자기 최대로 늘리지 않고 같은 단위 계열끼리 공유합니다 (판수·광고 / 메세지·피드 / 토너 발화 3종 / 비율 3종). 행마다 늘리면 막대가 다 꽉 차서 계열 간 크기 차이가 사라집니다. 반대로 계열이 다른 행끼리는 길이 비교가 불가합니다 — 그때는 숫자와 Δ만 보세요.

엄밀한 A/B가 아니라 전후 대조다

483은 9/2 배포분이라 사실상 오늘 세션이고, 482 이하는 3일 전체입니다. 같은 시간대에 유저를 무작위로 나눈 게 아니라 버전으로만 갈랐으므로, 업데이트를 먼저 받는 활성 유저 쪽으로 483이 기울어 있습니다. 483 표본이 하루 더 쌓이면 같은 날짜끼리 맞춰 다시 봐야 합니다. Δ는 483 이상 ÷ 482 이하입니다.

목표선은 마종, 초대만 퍼블마 — 창은 같은 3일

벤치도 솔리테어와 같은 캘린더 3일(8/31~9/2)로 뽑았습니다. 원본 관측 페이지는 게임 나이를 맞춘 D+n 창(마종 D+48~50)을 썼는데, 그걸 캘린더 창으로 바꿨으니 같은 D+n 대조가 아니라 "오늘 시점의 벤치 수준"이라는 눈금입니다. 그래서 목표선이 원본보다 낮습니다(마종 판수 11.3 → 7.5). 초대 2행은 마종·코지에 없는 지면이라 퍼블마를 씁니다.

Δ 색이 꺼진 3행이 있다

토너 생성시도 · 공유시도는 많을수록 좋은 지표가 아니라 벤치 수준으로 정상화가 목표이고, 토너 초대시도는 483이 의도적으로 끈 지면이라 0이 설계대로입니다. 이 3행은 증감에 색을 입히지 않고 회색으로 둡니다 — 색이 곧 좋고 나쁨으로 읽히면 판정을 오도합니다.

목표선은 채워졌고, 솔리테어 막대 2개는 값 대기

벤치 3사(코지·마종·퍼블마)는 8/31~9/2 실측이 들어와 🎯 목표선 9개가 그려집니다. 솔리테어 482 이하 / 483 이상 막대는 아직 —입니다 — 아래 1번 쿼리 결과를 받으면 채웁니다. 초대 유입률만 목표선도 비어 있습니다: 유입 세션은 entrypoint_now.entry로 세야 하는데, 483 세션 655건의 진입지면 어디에도 초대 계열 값이 없어 아직 특정되지 않았습니다.

갱신 쿼리 BigQuery 콘솔에 그대로 붙인다

1. 솔리테어 — 같은 3일치를 483 전후로 분리 (이 차트의 막대 원본) 
-- 벤치와 같은 캘린더 창(8/31~9/2)에서 client_version으로만 두 군을 갈랐다.
-- 483 = A/B 대조군 빌드(토너 초대 지면 차단) · 482 이하 = 비교군.
-- DAU는 세션이 아니라 1000_LOGIN_COMPLETE가 있는 (날짜, 플레이어) 쌍이다.
-- RV는 4210_RV_FINISH(일반 RV). 4110_INTERSTITIAL_RV_FINISH는 IRV로 다른 지면이라
-- 총광고에 넣지 않고 누락 확인용으로만 따로 센다.
SELECT
    CASE WHEN client_version >= 483 THEN '483이상' ELSE '482이하' END AS `구분`,
    COUNT(DISTINCT log_date) AS `일수`,
    COUNT(DISTINCT IF(has_login = 1, FORMAT('%t|%t', log_date, player_id), NULL)) AS `DAU`,
    COUNTIF(event = '2300_GAMEPLAY_FINISH')           AS `완료판수`,
    COUNTIF(event = '4210_RV_FINISH')                 AS `RV완료`,
    COUNTIF(event = '4010_INTERSTITIAL_AD_FINISH')    AS `IT완료`,
    COUNTIF(event = '4110_INTERSTITIAL_RV_FINISH')    AS `IRV완료`,
    COUNTIF(event = '3410_MSG_P2P_SUCCESS')           AS `메세지성공`,
    COUNTIF(event = '3510_FEED_SHARE_SUCCESS')        AS `피드성공`,
    COUNTIF(event = '3100_TOURNAMENT_CREATE')         AS `생성시도`,
    COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS') AS `생성성공`,
    COUNTIF(event = '3200_TOURNAMENT_SHARE')          AS `공유시도`,
    COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS')  AS `공유성공`,
    COUNTIF(event = '3460_MSG_P2P_INVITE'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대시도_토너`,
    COUNTIF(event = '3470_MSG_P2P_INVITE_SUCCESS'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대성공_토너`,
    COUNTIF(event = '3460_MSG_P2P_INVITE')            AS `초대시도_전체`
FROM (
    SELECT
        log_date, player_id, event, data, client_version,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE
        AND player_id > 0
)
GROUP BY `구분`
ORDER BY `구분` DESC;

빌드별로 쪼개 보려면 CASE 자리에 client_version을 넣고 GROUP BY도 그것으로 바꾸면 됩니다. 하루 안에 업데이트를 받은 플레이어는 같은 날 두 버전에 걸치므로 DAU가 두 군에 각각 한 번씩 잡힐 수 있습니다(비율 지표엔 영향이 작지만, 483 표본이 작을 때는 유의).

2. 진입지면 분포 — 초대 유입 세션을 세기 위한 사전 확인 
-- 초대 유입은 이벤트가 아니라 로그인 진입점이다. entrypoint_now는 STRING 컬럼이고
-- payload는 OBJECT라 중첩 경로로 바로 읽는다. 세션 = (player_id, logincount_total).
SELECT
    client_version AS `빌드`,
    IFNULL(JSON_VALUE(entrypoint_now, '$.entry'), '(null)') AS `진입지면`,
    COUNT(DISTINCT CONCAT(CAST(player_id AS STRING), '_',
                          CAST(logincount_total AS STRING))) AS `세션수`
FROM `game-log-359704.raw.solitaire_city_journey`
WHERE log_date BETWEEN '2026-09-01' AND CURRENT_DATE('Asia/Seoul')
    AND client_version >= 483
    AND is_dev IS DISTINCT FROM TRUE
    AND player_id > 0
GROUP BY `빌드`, `진입지면`
ORDER BY `빌드`, `세션수` DESC;

2026-09-02 실행 결과 — 초대 전용 진입지면이 없다. 483 세션 655건의 진입지면은 (null) 187 · in_game_menu 112 · ad 74 · bot_cta 67 · web_games_hub 59 · 이하 잔여로, 초대로 들어온 세션을 특정할 값이 보이지 않습니다. 초대 물량이 큰 퍼블마(3일 26,583시도)에 같은 쿼리를 돌려 초대량과 함께 커지는 지면을 찾아야 inv_in이 확정됩니다.

3. 벤치 3사 — 9/2 기준 3일치 (이 페이지의 목표선 원본) 
-- 코지·마종·퍼블마를 같은 캘린더 창(8/31~9/2)으로 뽑는다. D+n 정렬은 쓰지 않는다.
-- 9/2는 부분일이므로 DAU가 소폭 낮게 잡힌다.
WITH b AS (
    SELECT 'mahjong' AS proj, log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.mahjong`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0

    UNION ALL

    SELECT 'pubma', log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.puzzle_block_master`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0

    UNION ALL

    SELECT 'cozy', log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.cozy_tiles`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0
)
SELECT
    proj AS `프로젝트`,
    COUNT(DISTINCT log_date) AS `일수`,
    COUNT(DISTINCT IF(has_login = 1, FORMAT('%t|%t', log_date, player_id), NULL)) AS `DAU`,
    COUNTIF(event = '2300_GAMEPLAY_FINISH')           AS `완료판수`,
    COUNTIF(event = '4210_RV_FINISH')                 AS `RV완료`,
    COUNTIF(event = '4010_INTERSTITIAL_AD_FINISH')    AS `IT완료`,
    COUNTIF(event = '3410_MSG_P2P_SUCCESS')           AS `메세지성공`,
    COUNTIF(event = '3510_FEED_SHARE_SUCCESS')        AS `피드성공`,
    COUNTIF(event = '3100_TOURNAMENT_CREATE')         AS `생성시도`,
    COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS') AS `생성성공`,
    COUNTIF(event = '3200_TOURNAMENT_SHARE')          AS `공유시도`,
    COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS')  AS `공유성공`,
    COUNTIF(event = '3460_MSG_P2P_INVITE'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대시도_토너`,
    COUNTIF(event = '3470_MSG_P2P_INVITE_SUCCESS'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대성공_토너`
FROM b
GROUP BY `프로젝트`
ORDER BY `프로젝트`;
확인 범위 이벤트 매핑은 호출부 실측입니다 — 4210_RV_FINISH는 showRewardedAD 성공 시, 3460/3470_MSG_P2P_INVITE*는 FB.inviteAsync 직전·성공 시 (data.position = LogInvitePosition, 토너 초대는 tournament_invite). 벤치 3사 수치는 2026-09-02 실행 결과이고, 솔리테어 483 이상 구간은 값 대기입니다. inv_in(초대 유입 세션)만 미확정입니다.
