483 전후 벤치 대조

482 이하(8/31~9/4 · 7,245 유저-일)와 483 이상(9/2~9/6 · 11,091 유저-일)을 빌드별로 합산해 DAU당 지표 9개로 나란히 놓았습니다. 🎯 목표선은 8/31~9/2 벤치 고정 기준선 (마종 · 초대만 퍼블마)이라 솔리테어 창이 바뀌어도 움직이지 않습니다. 483 이상 막대에는 483 · 485 · 486 빌드가 함께 들어 있고, 배포 당일과 조회 당일은 하루가 잘려 있어 DAU를 분모로 쓰는 행이 구조적으로 눌립니다 — 방향 판단은 비율 2행(생성률·공유율)부터 보세요.

이전 구간482이하

바이럴 개편 전 빌드입니다. 9/2 저녁 배포 이후로는 사실상 전환이 끝나 9/3~9/6 의 482 잔량은 합쳐 7 유저-일뿐입니다.

현재 구간483이상

개편 후 빌드입니다. 이 막대에는 483 · 485 · 486 이 함께 들어 있습니다 — 토너 소셜 슬롯 A/B(485 ↔ 486)는 별도 문서에서 봅니다.

이건 A/B 가 아닙니다 — 같은 날 반반 서빙된 두 군이 아니라 앞뒤로 늘어선 두 구간입니다. 그래서 요일·이벤트·이용자 구성이 양쪽에 똑같이 걸리지 않습니다. 특히 483 이상은 배포 당일과 조회 당일이 하루씩 잘려 있어 DAU를 분모로 쓰는 행이 구조적으로 눌립니다 — 방향 판단은 비율 2행(생성률·공유율)부터 보세요. 초대 차단 코드(tournamentInviteEnabled)도 아직 커밋·배포 전이라 483 이상에도 토너 초대가 살아 있습니다.
솔리테어 BigQuery 목표선 = 마종 · 퍼블마 기준일 —

KPI 보드 DAU당 9행 · 빌드별 통산 · 막대 길이는 같은 단위 계열 안에서만 비교됩니다

벤치 3사 — 같은 3일치 코지 · 마종 · 퍼블마 · DAU당 · 8/31~9/2 고정

차트의 목표선은 마종 하나뿐이라 이 표를 함께 본다

막대 차트는 행마다 목표선을 한 줄만 그릴 수 있어 원본 규약대로 마종(초대는 퍼블마)을 얹었습니다. 하지만 판정이 갈릴 때 실제로 먼저 보는 건 코지이므로, 세 벤치를 같은 창으로 나란히 둔 표를 따로 실었습니다. 마종은 DAU가 압도적으로 커서 단독 비교가 함정이 될 수 있습니다.

초대 시도는 퍼블마만 값이 있다

토너 초대 지면(3460_MSG_P2P_INVITE · position=tournament_invite)은 마종·코지에 없어 0입니다. 그래서 그 행의 목표선만 퍼블마를 씁니다. 초대가 실제로 사람을 데려왔는지(유입률)는 이 문서에서 다루지 않습니다 — 분자·분모의 주체가 다르고(보낸 시도 ÷ 받은 세션) 유입에 시차가 있어 같은 창에서 읽으면 오독하기 쉽기 때문입니다.

목표선은 8/31~9/2 고정 기준선이다

벤치 3사는 8/31~9/2 한 번 뽑은 값을 그대로 고정해서 씁니다. 솔리테어 창이 바뀌어도 다시 뽑지 않습니다 — 목표선이 매번 같이 움직이면 무엇이 변한 건지 분간할 수 없기 때문입니다. 원본 관측 페이지는 게임 나이를 맞춘 D+n 창(마종 D+48~50)을 썼는데 이건 캘린더 창이라, 같은 D+n 대조가 아니라 "그 3일의 벤치 수준"이라는 눈금입니다. 그래서 목표선이 원본보다 낮습니다(마종 판수 11.3 → 7.5). 초대 2행은 마종·코지에 없는 지면이라 퍼블마를 씁니다.

원본 막대의 합산 재료입니다

조회 원본 — 날짜 × 빌드 (차트가 쓰지 않는 8/31 · 9/1 행 포함)

갱신 쿼리 BigQuery 콘솔에 그대로 붙인다

1. 솔리테어 — 날짜 × 빌드군 원본 (자동화가 매일 실행하는 쿼리 · log_date IN 은 결손일 목록이라 아래는 최근 3일을 넣은 예시) 
-- 이 문서를 채우는 쿼리다. scripts/refresh_sol_era_watch.py 가 매일 KST 09시에 이 문자열을
-- 그대로 실행하고, 같은 문자열을 문서의 SQL 폴드에 심는다 — 사본이 갈라질 수 없다.
--
-- 스캔 원칙
--  · 오늘은 절대 넣지 않는다. 마지막 날은 항상 어제다(log_date 는 KST 기준).
--  · 고정 창이 아니라 **결손일만** 읽는다. 평소에는 어제 하루뿐이라 스캔이 1일치로 고정된다.
--    (맥이 며칠 꺼져 있었으면 그 며칠이 한 번에 들어온다 — 공백이 영구 결손으로 남지 않는다.)
--  · 벤치 3사(코지·마종·퍼블마)는 이 쿼리에 없다. 8/31~9/2 고정 기준선이라 재조회하지 않는다.
--
-- 결과 1행 = 이 문서 DATA.sol.daily 1행. 별칭을 JS 키와 같게 둬서 옮겨 적을 때 매핑이 없다.
-- ★ver 는 client_version >= 483 을 한 군으로 묶은 값이다 — 485·486(슬롯 A/B)이 여기 섞인다.
--   2_VERSION 블록이 그날 실제로 뜬 빌드를 그대로 보여주므로 혼합 여부를 눈으로 확인할 수 있다.
-- DAU 는 세션이 아니라 1000_LOGIN_COMPLETE 가 있는 (날짜, 플레이어) 쌍이다.
-- RV 는 4210_RV_FINISH(일반 RV). 4110_INTERSTITIAL_RV_FINISH 는 IRV 로 다른 지면이라
-- 총광고에 넣지 않고 irv_fin 으로 누락 확인용으로만 센다.
-- 초대: inv_* = 토너 초대(position='tournament_invite'), inv_all_* = 지면 무관 전체.
WITH us AS (
    SELECT
        log_date, player_id, event, data, client_version,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date IN (DATE '2026-09-04', DATE '2026-09-05', DATE '2026-09-06')
        AND is_dev IS DISTINCT FROM TRUE
        AND player_id > 0
),
daily AS (
    SELECT
        CAST(log_date AS STRING) AS d,
        IF(client_version >= 483, '483', '482') AS ver,
        COUNT(DISTINCT IF(has_login = 1, player_id, NULL))                AS ud,
        COUNTIF(event = '2300_GAMEPLAY_FINISH')                           AS fin,
        COUNTIF(event = '4210_RV_FINISH')                                 AS rv_fin,
        COUNTIF(event = '4010_INTERSTITIAL_AD_FINISH')                    AS it_fin,
        COUNTIF(event = '4110_INTERSTITIAL_RV_FINISH')                    AS irv_fin,
        COUNTIF(event = '3410_MSG_P2P_SUCCESS')                           AS msg_ok,
        COUNTIF(event = '3510_FEED_SHARE_SUCCESS')                        AS feed_ok,
        COUNTIF(event = '3100_TOURNAMENT_CREATE')                         AS cr_try,
        COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS')                 AS cr_ok,
        COUNTIF(event = '3200_TOURNAMENT_SHARE')                          AS sh_try,
        COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS')                  AS sh_ok,
        COUNTIF(event = '3460_MSG_P2P_INVITE'
                AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS inv_try,
        COUNTIF(event = '3470_MSG_P2P_INVITE_SUCCESS'
                AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS inv_ok,
        COUNTIF(event = '3460_MSG_P2P_INVITE')                            AS inv_all_try,
        COUNTIF(event = '3470_MSG_P2P_INVITE_SUCCESS')                    AS inv_all_ok
    FROM us
    GROUP BY d, ver
),
vers AS (
    -- 483 이상 막대에 실제로 어떤 빌드가 섞여 있는지. 같은 us 를 다시 쓰므로 추가 스캔이 없다.
    SELECT
        CAST(log_date AS STRING) AS d,
        CAST(client_version AS STRING) AS ver,
        COUNT(DISTINCT IF(has_login = 1, player_id, NULL)) AS ud
    FROM us
    GROUP BY d, ver
)
SELECT '0_META' AS blk, TO_JSON_STRING(STRUCT(
    FORMAT_TIMESTAMP('%Y-%m-%d %H:%M', CURRENT_TIMESTAMP(), 'Asia/Seoul') AS pulled_kst,
    CAST(DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY) AS STRING)              AS last_day)) AS payload
UNION ALL
SELECT '1_DAILY', TO_JSON_STRING(ARRAY_AGG(STRUCT(
    d, ver, ud, fin, rv_fin, it_fin, irv_fin, msg_ok, feed_ok,
    cr_try, cr_ok, sh_try, sh_ok, inv_try, inv_ok, inv_all_try, inv_all_ok)
    ORDER BY d, ver DESC)) FROM daily
UNION ALL
SELECT '2_VERSION', TO_JSON_STRING(ARRAY_AGG(STRUCT(d, ver, ud)
    ORDER BY d, ver)) FROM vers
ORDER BY blk

ver는 483 이상을 전부 하나로 묶은 값입니다. 484·485가 배포되면 차단 빌드와 비차단 빌드가 같은 막대에 섞이므로, IF(...) 자리에 client_version을 그대로 넣고 GROUP BY도 바꿔 버전별로 먼저 확인하세요. 하루 안에 업데이트를 받은 플레이어는 같은 날 두 버전에 걸치므로 DAU가 두 군에 각각 한 번씩 잡힐 수 있습니다(비율 지표엔 영향이 작지만, 483 표본이 작을 때는 유의).

2. 벤치 3사 — 8/31~9/2 (고정 기준선을 뽑은 쿼리 · 재실행하지 않는다) 
-- 코지·마종·퍼블마를 같은 캘린더 창(8/31~9/2)으로 뽑는다. D+n 정렬은 쓰지 않는다.
-- ★이 결과는 고정 기준선으로 박아두고 다시 돌리지 않는다 — 목표선이 매번 흔들리면
--   솔리테어 쪽 변화를 읽을 수 없다. 기준선을 옮기려면 그 사실을 문서에 남긴다.
WITH b AS (
    SELECT 'mahjong' AS proj, log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.mahjong`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0

    UNION ALL

    SELECT 'pubma', log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.puzzle_block_master`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0

    UNION ALL

    SELECT 'cozy', log_date, player_id, event, data,
        MAX(IF(event = '1000_LOGIN_COMPLETE', 1, 0))
            OVER (PARTITION BY log_date, player_id) AS has_login
    FROM `game-log-359704.raw.cozy_tiles`
    WHERE log_date BETWEEN '2026-08-31' AND '2026-09-02'
        AND is_dev IS DISTINCT FROM TRUE AND player_id > 0
)
SELECT
    proj AS `프로젝트`,
    COUNT(DISTINCT log_date) AS `일수`,
    COUNT(DISTINCT IF(has_login = 1, FORMAT('%t|%t', log_date, player_id), NULL)) AS `DAU`,
    COUNTIF(event = '2300_GAMEPLAY_FINISH')           AS `완료판수`,
    COUNTIF(event = '4210_RV_FINISH')                 AS `RV완료`,
    COUNTIF(event = '4010_INTERSTITIAL_AD_FINISH')    AS `IT완료`,
    COUNTIF(event = '3410_MSG_P2P_SUCCESS')           AS `메세지성공`,
    COUNTIF(event = '3510_FEED_SHARE_SUCCESS')        AS `피드성공`,
    COUNTIF(event = '3100_TOURNAMENT_CREATE')         AS `생성시도`,
    COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS') AS `생성성공`,
    COUNTIF(event = '3200_TOURNAMENT_SHARE')          AS `공유시도`,
    COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS')  AS `공유성공`,
    COUNTIF(event = '3460_MSG_P2P_INVITE'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대시도_토너`,
    COUNTIF(event = '3470_MSG_P2P_INVITE_SUCCESS'
            AND JSON_VALUE(data, '$.position') = 'tournament_invite') AS `초대성공_토너`
FROM b
GROUP BY `프로젝트`
ORDER BY `프로젝트`;
확인 범위 이벤트 매핑은 호출부 실측입니다 — 4210_RV_FINISH는 showRewardedAD 성공 시, 3460/3470_MSG_P2P_INVITE*는 FB.inviteAsync 직전·성공 시 (data.position = LogInvitePosition, 토너 초대는 tournament_invite). 벤치 3사 수치는 2026-09-02 실행 결과를 고정한 기준선이고, 솔리테어는 2026-09-04 조회분입니다(9/4는 부분 집계). 초대 유입 세션은 이 문서 범위 밖입니다.

이 문서가 답하지 않는 것 9행 모두 실측이라 빈칸은 없지만, 이 표는 발화량과 전환율까지만 말합니다 — 초대·공유가 실제로 사람을 데려왔는지는 유입 세션을 세야 하고, 분자·분모의 주체가 달라(보낸 시도 ÷ 받은 세션) 별도 문서에서 다룰 문제입니다. 483이 A/B 대조군이 아니라는 점도 그대로입니다.
