실사용 중 Max 개인 설정 원문 Claude Code / Opus 5 기준 2026-09-10

왜 이 두 개인가 규칙은 적을수록 지켜집니다

규칙을 많이 넣으면 지켜지지 않습니다. CLAUDE.md 는 매 세션 전문이 컨텍스트에 올라가기 때문에, 길어질수록 비용도 늘고 정작 중요한 줄이 묻힙니다. 그래서 돈이 새는 지점 두 곳만 막았습니다.

규칙 막는 손실 없을 때 실제로 벌어지는 일
① 작업 워크플로우
승인 게이트		 잘못된 방향으로 쌓인 구현 요청 한 줄에 곧바로 파일 여러 개를 고칩니다. 방향이 틀렸다는 걸 200줄쯤 지나서 알게 되고, 그때부터는 되돌리는 것도 일이 됩니다.
② 병렬 수행
모델 배치		 순차 대기 시간 · 토큰 낭비 서로 관계없는 작업 5개를 하나씩 순서대로 합니다. 반대로 병렬만 켜면 서브에이전트가 각자 장황하게 보고해서 토큰이 더 나갑니다.
이 표를 읽는 법

두 규칙은 성격이 다릅니다. ①은 항상 강제돼야 하는 제약이라 CLAUDE.md 에 둬야 하고(스킬로 빼면 "안 불러오면 그만"이 됩니다), ②는 조건부로만 필요한 절차라 나중에 스킬로 분리해도 됩니다. 지금은 둘 다 CLAUDE.md 에 있습니다.

① 작업 워크플로우 승인 전에는 구현에 손대지 않는다

핵심은 4번과 5번입니다. 계획을 세우는 것까지는 시키지 않아도 하지만, 계획을 세운 뒤 멈추는 것은 명시하지 않으면 하지 않습니다.

단계 하는 일 이 단계가 없으면
1. 분석 우선 요청이 와도 구현하지 않고 코드베이스부터 읽습니다. 잘못된 전제 위에 구현이 쌓입니다.
2. research.md 분석 결과를 프로젝트 _ignore/research.md 로 남깁니다. 다음 세션에서 같은 분석을 처음부터 다시 합니다.
3. plan.md 구현 계획을 _ignore/plan.md 로 씁니다. 머릿속에만 있는 계획은 검토할 수가 없습니다.
4. 검토 대기 사람이 계획을 읽고 주석을 달 때까지 멈춥니다. 계획서를 쓰고 그대로 자기가 실행해버립니다.
5. 승인 게이트 승인 전에는 구현 파일을 건드리지 않습니다. "계획 좋네요" 한마디에 이미 절반이 고쳐져 있습니다.
6. 기계적 실행 승인된 계획만 그대로 실행합니다. 임의 판단 금지. 실행 중에 "이게 더 나을 것 같아서" 범위가 번집니다.
7. 되돌리기 방향이 틀렸으면 덧대지 말고 revert 후 다시 계획합니다. 틀린 코드 위에 수정이 겹겹이 쌓입니다.
문서를 _ignore/ 에 두는 이유

research.md · plan.md 는 작업 부산물이지 산출물이 아닙니다. 프로젝트 루트에 두면 커밋에 섞여 들어가고, 전역에 두면 프로젝트 컨텍스트를 잃습니다. 그래서 각 프로젝트의 git-ignore 대상 폴더 안에 둡니다.

📍 헤더를 쓰는 이유

모든 답변 첫 줄에 📍 1. 분석 우선 (40%) 처럼 현재 단계를 찍게 했습니다. 게이트를 넘었는지 한 줄만 보고 판단하기 위해서입니다. 답변이 길어져도 지금 분석 중인지 이미 구현에 들어갔는지가 맨 위에서 보입니다.

# 작업 워크플로우 (전역 규칙)

모든 프로젝트/모든 파일 작업에 이 플로우를 따른다. 승인 없이는 구현하지 않는다.

1. **분석 우선** — 요청이 오면 바로 구현하지 말고 먼저 코드베이스를 분석한다.
2. **research.md** — 분석 결과를 해당 프로젝트 폴더의 `research.md`로 남긴다.
3. **plan.md** — 구현 계획을 해당 프로젝트 폴더의 `plan.md`로 작성한다.
4. **검토 대기** — 개발자가 직접 계획을 검토하고 주석을 달 때까지 기다린다.
5. **승인 게이트** — 계획이 승인되기 전에는 구현에 손대지 않는다.
6. **기계적 실행** — 승인된 계획만 그대로 실행한다. 임의 판단으로 벗어나지 않는다.
7. **되돌리기 원칙** — 방향이 틀렸으면 그 위에 덧대지 말고 되돌린(revert) 뒤 다시 계획한다.

## 문서 위치
- `research.md`, `plan.md` 등 작업 문서는 **각 프로젝트 폴더 안, 그중에서도 git-ignore 대상 폴더**(예: `_ignore/`)에 둔다 (전역이 아님, 프로젝트 루트에 그대로 두지도 않음).
- 해당 프로젝트의 `.gitignore`에 이미 이런 용도의 폴더가 있으면 그걸 쓰고, 없으면 새로 만들어 `.gitignore`에 등록한 뒤 그 안에 저장한다.
- 각 프로젝트의 컨텍스트로 관리한다.

## 답변 상태 표시 (필수)
모든 답변의 **맨 첫 줄**에 현재 워크플로우 단계와 진행률을 표시한 뒤 본문을 이어간다.

형식: `📍 [단계번호]. [단계명] (n%)`

예:
```
📍 1. 분석 우선 (40%)
```
- 단계번호/단계명은 위 워크플로우 1~7 기준.
- `n%`는 해당 단계의 진행 정도(그 단계가 얼마나 완료됐는지) 추정치.
- 작업이 없거나 대기 상태면 그 상태를 명시(예: `대기 중 · 작업 없음`).

② 병렬 수행 총괄은 한 명, 잡일은 뿌린다

독립적인 하위 작업으로 쪼개지면 무조건 병렬로 돌립니다. 다만 병렬 자체가 목적은 아닙니다 — 앞 작업 결과가 뒤 작업의 입력이면 그냥 순차로 갑니다.

모델 맡기는 일 비고
Opus 5 설계 · 아키텍처 판단 · 복잡한 버그 추적 · 크로스 파일 리팩터링 · 최종 검증 총괄도 겸합니다. 직접 잡일은 하지 않습니다.
Sonnet 5 일반 구현 · 코드 리뷰 · 문서 작성 · 중간 난이도 분석 기본값으로 두기 좋은 자리입니다.
Haiku 4.5 단순 검색 · 파일 목록화 · 반복 기계 작업 · 포맷 변환 판단이 섞이면 바로 한 단계 올립니다.
이 규칙에서 제일 중요한 건 3-1 (출력 최소화)

이걸 빼면 병렬이 오히려 토큰을 더 먹습니다. 서브에이전트가 각자 "무엇을 할 계획이고 무엇을 했는지"를 장황하게 보고하는데, 그 서술은 총괄에게 전부 넘어오고 사용자는 어차피 읽지 않습니다. 그래서 서브에이전트에게는 산출물 형식을 미리 못박아 주고 그 외 텍스트를 금지합니다.

4번 검증은 생략하면 안 됩니다

서브에이전트가 "고쳤습니다" 라고 보고만 하고 실제 파일은 안 고친 경우가 실제로 나옵니다. 총괄이 작업 하나하나 직접 확인하는 단계를 넣어야 합니다 — 범위를 지켰는지, 코드에 반영됐는지, 작업 간 충돌·스타일 불일치가 없는지.

사용자에게 말하는 주체는 총괄 하나뿐

서브에이전트의 원문이나 중간 로그를 그대로 옮기지 않습니다. 검증까지 끝난 뒤 총괄이 한 번에 짧게 정리해서 공유합니다 — 어떤 작업을 어떤 모델에 맡겼는지, 결과 요약, 검증에서 잡아 고친 것, 남은 이슈.

# 병렬 수행 규칙 (전역 규칙)

요청이 **독립적인 하위 작업으로 쪼개질 수 있으면 무조건 병렬로 수행**한다. 순차로 해야 할 이유(앞 작업 결과가 뒤 작업의 입력)가 있을 때만 순차로 간다.

## 1. 총괄(오케스트레이터)
- 세션의 **가장 성능 좋은 모델**(현재 Opus 5)이 총괄을 맡는다. 총괄은 직접 잡일을 하지 않고 분해·배치·검증·통합만 한다.
- 총괄이 하는 일: 작업 분해 → 서브에이전트별 모델 배치 → 병렬 실행 → **결과 검증 및 개선** → 최종 공유.

## 2. 모델 배치
작업 성격에 맞는 모델을 골라 `Agent` 호출의 `model`로 지정한다.
- **Opus 5** — 설계, 아키텍처 판단, 복잡한 버그 추적, 크로스 파일 리팩터링, 최종 검증
- **Sonnet 5** — 일반 구현, 코드 리뷰, 문서 작성, 중간 난이도 분석
- **Haiku 4.5** — 단순 검색/수집, 파일 목록화, 반복적 기계 작업, 포맷 변환
- 애매하면 한 단계 위 모델로 올린다. 잘못 배치해서 다시 하는 비용이 더 크다.

## 3. 실행
- 독립 작업은 **한 메시지에 여러 `Agent` 호출**을 넣어 동시에 띄운다. 하나씩 순차로 띄우지 않는다.
- 각 서브에이전트에게는 목표·산출물 형식·건드리면 안 되는 범위를 명시한다.

## 3-1. 서브에이전트 출력 최소화 (토큰 절약, 필수)
사용자는 **총괄한테서만** 보고를 받는다. 서브에이전트의 중간 서술은 전부 낭비다.
각 `Agent` 프롬프트에 아래를 항상 넣는다:
- "진행 상황 서술·계획 설명·했던 일 나열·인사말·요약 반복 금지."
- "최종 응답은 **결과물만** 담는다. 지정한 형식(예: JSON, 변경 파일 목록, 결론 한 줄) 외 어떤 텍스트도 붙이지 않는다."
- "파일을 수정했으면 diff 전문이나 코드 전문을 되돌려주지 말고 `경로:라인` + 한 줄 설명만 반환한다."
- 산출물 형식을 총괄이 **미리 못박아** 준다. 형식을 안 주면 서브에이전트가 장황해진다.

## 4. 검증 및 개선 (생략 금지)
서브에이전트 결과를 그대로 믿지 않는다. 총괄이 **작업 하나하나** 직접 확인한다.
- 결과물이 요청 범위를 지켰는지
- 실제 코드/파일에 반영됐는지 (보고만 하고 안 한 경우 잡아낸다)
- 작업 간 충돌·중복·스타일 불일치가 없는지
- 부족하면 총괄이 직접 고치거나 해당 서브에이전트를 다시 돌린다.

## 5. 최종 공유
**사용자에게 말하는 주체는 총괄 하나뿐이다.** 서브에이전트의 원문·중간 로그·작업 서술을 사용자에게 그대로 옮기지 않는다.
검증까지 끝난 뒤 총괄이 한 번에, 짧게 정리해서 공유한다.
- 어떤 작업을 어떤 모델에 맡겼는지 (한 줄씩)
- 각 결과 요약 (한 줄씩)
- 검증에서 잡아 고친 것
- 남은 이슈 / 확인 필요한 것

최종 공유도 간결하게. 과정 재생 금지, 결과와 판단만.

## 주의
- 이 규칙은 위 **작업 워크플로우(분석 → research.md → plan.md → 승인 게이트)** 를 대체하지 않는다. 병렬화는 각 단계 **안에서** 적용한다. 승인 없이 구현으로 넘어가는 건 여전히 금지.
- 작업이 하나거나 서로 의존적이면 억지로 쪼개지 않는다. 병렬 자체가 목적이 아니다.

붙여넣기 어디에 두느냐로 적용 범위가 갈립니다

위치 적용 범위 이럴 때

<repo>/CLAUDE.md 그 레포에서 작업하는 사람 전원 팀 규칙으로 강제할 때. 커밋하면 자동 적용됩니다.
둘 다 둘 다 로딩됩니다 전역엔 개인 취향, 레포엔 팀 규칙으로 나눠 담습니다.
적용됐는지 확인하는 법

새 세션에서 아무 작업이나 시켜 보고, 답변 첫 줄에 📍 헤더가 뜨면 걸린 것입니다. 안 뜨면 파일 위치가 틀렸거나 세션이 규칙을 읽기 전에 시작된 경우입니다.

# 작업 워크플로우 (전역 규칙)

모든 프로젝트/모든 파일 작업에 이 플로우를 따른다. 승인 없이는 구현하지 않는다.

1. **분석 우선** — 요청이 오면 바로 구현하지 말고 먼저 코드베이스를 분석한다.
2. **research.md** — 분석 결과를 해당 프로젝트 폴더의 `research.md`로 남긴다.
3. **plan.md** — 구현 계획을 해당 프로젝트 폴더의 `plan.md`로 작성한다.
4. **검토 대기** — 개발자가 직접 계획을 검토하고 주석을 달 때까지 기다린다.

## 문서 위치
- `research.md`, `plan.md` 등 작업 문서는 **각 프로젝트 폴더 안, 그중에서도 git-ignore 대상 폴더**(예: `_ignore/`)에 둔다 (전역이 아님, 프로젝트 루트에 그대로 두지도 않음).
- 해당 프로젝트의 `.gitignore`에 이미 이런 용도의 폴더가 있으면 그걸 쓰고, 없으면 새로 만들어 `.gitignore`에 등록한 뒤 그 안에 저장한다.
- 각 프로젝트의 컨텍스트로 관리한다.

## 답변 상태 표시 (필수)
모든 답변의 **맨 첫 줄**에 현재 워크플로우 단계와 진행률을 표시한 뒤 본문을 이어간다.

형식: `📍 [단계번호]. [단계명] (n%)`

예:
```
📍 1. 분석 우선 (40%)
```
- 단계번호/단계명은 위 워크플로우 1~7 기준.
- `n%`는 해당 단계의 진행 정도(그 단계가 얼마나 완료됐는지) 추정치.
- 작업이 없거나 대기 상태면 그 상태를 명시(예: `대기 중 · 작업 없음`).

# 병렬 수행 규칙 (전역 규칙)

요청이 **독립적인 하위 작업으로 쪼개질 수 있으면 무조건 병렬로 수행**한다. 순차로 해야 할 이유(앞 작업 결과가 뒤 작업의 입력)가 있을 때만 순차로 간다.

## 1. 총괄(오케스트레이터)
- 세션의 **가장 성능 좋은 모델**(현재 Opus 5)이 총괄을 맡는다. 총괄은 직접 잡일을 하지 않고 분해·배치·검증·통합만 한다.
- 총괄이 하는 일: 작업 분해 → 서브에이전트별 모델 배치 → 병렬 실행 → **결과 검증 및 개선** → 최종 공유.

## 2. 모델 배치
작업 성격에 맞는 모델을 골라 `Agent` 호출의 `model`로 지정한다.
- **Opus 5** — 설계, 아키텍처 판단, 복잡한 버그 추적, 크로스 파일 리팩터링, 최종 검증
- **Sonnet 5** — 일반 구현, 코드 리뷰, 문서 작성, 중간 난이도 분석
- **Haiku 4.5** — 단순 검색/수집, 파일 목록화, 반복적 기계 작업, 포맷 변환
- 애매하면 한 단계 위 모델로 올린다. 잘못 배치해서 다시 하는 비용이 더 크다.

## 3. 실행
- 독립 작업은 **한 메시지에 여러 `Agent` 호출**을 넣어 동시에 띄운다. 하나씩 순차로 띄우지 않는다.
- 각 서브에이전트에게는 목표·산출물 형식·건드리면 안 되는 범위를 명시한다.

## 3-1. 서브에이전트 출력 최소화 (토큰 절약, 필수)
사용자는 **총괄한테서만** 보고를 받는다. 서브에이전트의 중간 서술은 전부 낭비다.
각 `Agent` 프롬프트에 아래를 항상 넣는다:
- "진행 상황 서술·계획 설명·했던 일 나열·인사말·요약 반복 금지."
- "최종 응답은 **결과물만** 담는다. 지정한 형식(예: JSON, 변경 파일 목록, 결론 한 줄) 외 어떤 텍스트도 붙이지 않는다."
- "파일을 수정했으면 diff 전문이나 코드 전문을 되돌려주지 말고 `경로:라인` + 한 줄 설명만 반환한다."
- 산출물 형식을 총괄이 **미리 못박아** 준다. 형식을 안 주면 서브에이전트가 장황해진다.

## 4. 검증 및 개선 (생략 금지)
서브에이전트 결과를 그대로 믿지 않는다. 총괄이 **작업 하나하나** 직접 확인한다.
- 결과물이 요청 범위를 지켰는지
- 실제 코드/파일에 반영됐는지 (보고만 하고 안 한 경우 잡아낸다)
- 작업 간 충돌·중복·스타일 불일치가 없는지
- 부족하면 총괄이 직접 고치거나 해당 서브에이전트를 다시 돌린다.

## 5. 최종 공유
**사용자에게 말하는 주체는 총괄 하나뿐이다.** 서브에이전트의 원문·중간 로그·작업 서술을 사용자에게 그대로 옮기지 않는다.
검증까지 끝난 뒤 총괄이 한 번에, 짧게 정리해서 공유한다.
- 어떤 작업을 어떤 모델에 맡겼는지 (한 줄씩)
- 각 결과 요약 (한 줄씩)
- 검증에서 잡아 고친 것
- 남은 이슈 / 확인 필요한 것

최종 공유도 간결하게. 과정 재생 금지, 결과와 판단만.

## 주의
- 이 규칙은 위 **작업 워크플로우(분석 → research.md → plan.md → 승인 게이트)** 를 대체하지 않는다. 병렬화는 각 단계 **안에서** 적용한다. 승인 없이 구현으로 넘어가는 건 여전히 금지.
- 작업이 하나거나 서로 의존적이면 억지로 쪼개지 않는다. 병렬 자체가 목적이 아니다.
