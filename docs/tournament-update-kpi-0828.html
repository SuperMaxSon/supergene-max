어디서 죽는가 8/28 · 기존 유저 · 클리어 11,862판

병목은 코드가 아니라 지면입니다

생성 실패 1,719건 중 1,598건(92.9%)이 USER_INPUT — 유저가 다이얼로그를 그대로 닫은 겁니다. 그리고 한 번 닫으면 거절 카운터가 올라가 이후 시도가 억제되므로 (3130 4,585건), 실패와 억제는 같은 현상의 앞뒤입니다. 앞단에서 물량을 늘리는 수정으로는 이 구간을 통과할 수 없습니다.

이 퍼널은 어떻게 뽑았나 — 생성/공유 카운트 + 실패 사유 
-- 분모는 세션이 아니라 "클리어 판수". 토너 공유·생성은 클리어 시점에만 발사되므로
-- 세션당으로 보면 UA 축소로 바뀐 플레이 강도가 그대로 섞여 들어온다.
WITH base AS (
  SELECT
    log_date, event,
    JSON_VALUE(data, '$.result')     AS result,
    JSON_VALUE(data, '$.error_code') AS error_code,
    IF(logincount_total <= 1, 'nru', 'existing') AS cohort
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date BETWEEN '2026-08-20' AND '2026-08-28'
)
SELECT
  log_date,
  COUNTIF(event = '2300_GAMEPLAY_FINISH' AND result = 'clear') AS clears,
  COUNTIF(event = '3100_TOURNAMENT_CREATE')            AS create_try,
  COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS')    AS create_ok,
  COUNTIF(event = '3120_TOURNAMENT_CREATE_FAIL')       AS create_fail,
  COUNTIF(event = '3130_TOURNAMENT_CREATE_SUPPRESSED') AS create_supp,
  COUNTIF(event = '3200_TOURNAMENT_SHARE')             AS share_try,
  COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS')     AS share_ok
FROM base
WHERE cohort = 'existing'
GROUP BY log_date
ORDER BY log_date;

-- 실패 사유 분해 (USER_INPUT 비중)
SELECT
  log_date,
  JSON_VALUE(data, '$.error_code') AS error_code,
  COUNT(*) AS fail_count,
  ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY log_date), 1) AS pct
FROM `game-log-359704.raw.solitaire_city_journey`
WHERE log_date BETWEEN '2026-08-26' AND '2026-08-28'
  AND event = '3120_TOURNAMENT_CREATE_FAIL'
  AND logincount_total > 1
GROUP BY log_date, error_code
ORDER BY log_date, fail_count DESC;

배포 전후 클리어 100판당 · 기존 유저 · 세로 점선이 8/27 배포

P2P만 밴드를 벗어났습니다

남이 만든 토너먼트를 친구 대전으로 잘못 분류하던 문제를 고치자 오발송이 배포일부터 범위 밖으로 내려갔습니다. 다만 빠진 물량이 공유·생성 어느 쪽으로도 넘어가지 않아, 줄어든 만큼 유입이 늘지는 않았습니다.

이 차트는 어떻게 뽑았나 — 코호트 분리 + 100클리어 정규화 
-- UA를 줄이면 NRU가 통째로 빠져 남은 코호트가 기존 유저로 쏠린다.
-- 그럼 클리어당 공유 자격자 비중이 저절로 올라가므로 코호트를 반드시 분리한다.
WITH base AS (
  SELECT
    log_date, client_version, event,
    JSON_VALUE(data, '$.result') AS result,
    JSON_VALUE(data, '$.reason') AS reason,
    IF(logincount_total <= 1, 'nru', 'existing') AS cohort
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date BETWEEN '2026-08-20' AND '2026-08-28'
)
SELECT
  log_date, cohort,
  MAX(client_version) AS max_build,          -- 배포 반영 확인용 (474 → 477)
  COUNTIF(event = '2300_GAMEPLAY_FINISH' AND result = 'clear') AS clears,
  ROUND(COUNTIF(event = '3200_TOURNAMENT_SHARE') * 100.0
        / NULLIF(COUNTIF(event = '2300_GAMEPLAY_FINISH' AND result = 'clear'), 0), 2) AS share_try_per_100_clear,
  ROUND(COUNTIF(event = '3400_MSG_P2P') * 100.0
        / NULLIF(COUNTIF(event = '2300_GAMEPLAY_FINISH' AND result = 'clear'), 0), 2) AS p2p_per_100_clear,
  COUNTIF(event = '3230_TOURNAMENT_SHARE_SUPPRESSED' AND reason = 'no_tournament') AS supp_no_tournament,
  COUNTIF(event = '3230_TOURNAMENT_SHARE_SUPPRESSED' AND reason = 'first_nru')     AS supp_first_nru
FROM base
GROUP BY log_date, cohort
ORDER BY log_date, cohort;

유입 구성 비중이 아니라 절대수로 봐야 하는 구간

"인게임 메뉴 26.8%"를 성과로 읽으면 안 됩니다

비중이 오른 주된 이유는 분모인 광고 유입이 8,305 → 1,307로 84% 빠졌기 때문입니다 (UA 집행 축소, 확인됨). 절대수도 1,076 → 1,519로 늘긴 했지만 이는 복귀 유입이지 신규 획득이 아닙니다. 그리고 이번 배포가 노린 feed 유입은 92~144 밴드에서 전혀 움직이지 않았습니다.

이 그래프는 어떻게 뽑았나 — 진입점별 세션 수 
-- 세션 = (player_id, logincount_total) 한 쌍. BigQuery는 COUNT(DISTINCT struct)를
-- 허용하지 않으므로 문자열 복합키로 만든다.
WITH sessions AS (
  SELECT
    log_date,
    CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS session_key,
    JSON_VALUE(entrypoint_now, '$.entry') AS entry
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date BETWEEN '2026-08-20' AND '2026-08-28'
  GROUP BY log_date, session_key, entry
)
SELECT
  log_date, entry,
  COUNT(DISTINCT session_key) AS sessions,
  ROUND(COUNT(DISTINCT session_key) * 100.0
        / SUM(COUNT(DISTINCT session_key)) OVER (PARTITION BY log_date), 2) AS pct
FROM sessions
WHERE entry IS NOT NULL
GROUP BY log_date, entry
ORDER BY log_date, sessions DESC;

지금은 고치지 않습니다

거절 카운터가 USER_INPUT에만 증가해 PENDING_REQUEST 실패는 억제 게이트에 걸리지 않는 구조입니다 — 루프가 구조적으로 가능합니다. 다만 무엇이 재호출을 트리거하는지 미상이라, 가드만 넣으면 증상만 덮습니다. 재현 경로 확보가 선행돼야 합니다.

이 판정은 어떻게 뽑았나 — 세션 교차 + 집중도 
-- ① 폴백을 탄 세션과 안 탄 세션의 PENDING_REQUEST 발생률 비교 (생성 시도 세션만)
WITH ev AS (
  SELECT
    log_date,
    CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS session_key,
    event,
    JSON_VALUE(data, '$.reason')     AS reason,
    JSON_VALUE(data, '$.error_code') AS error_code
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date BETWEEN '2026-08-27' AND '2026-08-28'
    AND logincount_total > 1
),
s AS (
  SELECT
    log_date, session_key,
    LOGICAL_OR(event = '3100_TOURNAMENT_CREATE') AS had_create,
    LOGICAL_OR(event = '3230_TOURNAMENT_SHARE_SUPPRESSED' AND reason = 'no_tournament') AS had_fallback,
    LOGICAL_OR(event = '3120_TOURNAMENT_CREATE_FAIL' AND error_code = 'PENDING_REQUEST') AS had_pending
  FROM ev GROUP BY log_date, session_key
)
SELECT
  log_date, had_fallback,
  COUNT(*) AS sessions_with_create,
  COUNTIF(had_pending) AS sessions_with_pending,
  ROUND(COUNTIF(had_pending) * 100.0 / NULLIF(COUNT(*), 0), 2) AS pending_rate_pct
FROM s WHERE had_create
GROUP BY log_date, had_fallback
ORDER BY log_date, had_fallback;

-- ② 집중도 — 세션당 몇 건씩 터졌나
WITH ev AS (
  SELECT
    CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS session_key,
    COUNT(*) AS pending_count
  FROM `game-log-359704.raw.solitaire_city_journey`
  WHERE log_date = '2026-08-28'
    AND event = '3120_TOURNAMENT_CREATE_FAIL'
    AND JSON_VALUE(data, '$.error_code') = 'PENDING_REQUEST'
  GROUP BY session_key
)
SELECT pending_count, COUNT(*) AS sessions
FROM ev GROUP BY pending_count ORDER BY pending_count DESC;
