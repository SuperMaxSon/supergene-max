이 표를 읽는 법

솔리테어 08-14~17 실측입니다. 같은 상황·같은 에러인데 iOS만 문장 끝에 마침표가 붙어 옵니다. 복구 조건이 error.message === "An unexpected error occurred"라서, 마침표가 붙은 51건은 FB에 이미 만들어진 토너먼트를 조회조차 하지 않고 버렸습니다. 조건을 넓히는 방향의 변경이므로 기존에 통과하던 Android 599건의 동작은 바뀌지 않습니다.

우리만의 문제가 아닙니다

포팅 원본(코지타일즈)부터 같은 정확 일치 비교를 쓰고 있고, 그걸 물려받은 프로젝트 전부가 동일합니다. 즉 어느 프로젝트든 iOS 복구 누락분이 그대로 남아 있습니다.

핵심은 이 헬퍼 하나입니다.

/** 생성 실패가 "FB에는 만들어졌을 수 있는" NETWORK_FAILURE인지. iOS는 같은 메시지가 끝에 마침표를 달고 온다. */
private isRecoverableCreateFailure(error: { code: string; message: string }): boolean {
    if (error?.code !== "NETWORK_FAILURE") {
        return false;
    }
    return (error.message ?? "").trim().replace(/\.+$/, "") === "An unexpected error occurred";
}
왜 헬퍼로 묶었나 — 상수 중복이 재발 원인

솔리테어도 같은 문자열 상수를 두 곳에서 각자 선언해 각자 비교하고 있었습니다. 한 곳만 정규화하면 다른 곳에서 같은 결함이 다시 살아납니다. 그래서 선언과 비교를 헬퍼 1개로 수렴시키고 비교 지점들이 그것을 호출하게 했습니다. trim() → 마침표 제거 순서도 지켜야 합니다(뒤 공백이 붙어 오는 케이스가 있습니다).

선행 정리 — 복구에 성공했을 때의 로그

이 수정 전에 커밋 6065577c로 로그를 먼저 정리했습니다. 복구로 살린 건인데 실패 로그가 이미 찍혀 있으면 생성 1회에 실패+성공이 동시에 남습니다(if (!tournament) 가드). 그리고 복구분 성공 로그에 recovered: "1"을 실어야 복구가 실제로 몇 건을 살렸는지 나중에 셀 수 있습니다.

채택하지 않은 대안

code === "NETWORK_FAILURE"만 보고 메시지 비교를 없애는 방안. 조건이 필요 이상으로 넓어지고 다른 프로젝트와 판정 기준이 갈라져서 문구 정규화를 택했습니다.

이식 전 주의 기대치와 측정

수락률 상승을 기대치로 잡지 마세요

솔리테어에서 복구 성공 건수는 수정 전후 모두 사실상 0입니다. 조건을 이미 통과했던 Android 599건에서도 0이었습니다. 즉 "FB가 실제로는 안 만들었다"는 가설이 아직 배제되지 않았습니다. 이번 수정의 실질 성과는 특정 기기 구제 + 재발 감지 장치 확보로 읽는 것이 정확합니다.

계측을 같은 빌드에 태우세요

정규화만 내보내면 효과를 측정할 방법이 없습니다. 솔리테어는 실패 로그 payload에 recover(hit / nomatch / empty / skip / error) + list_size 2필드를 더했습니다. 프리폼 payload를 쓰는 프로젝트면 신규 로그코드 없이 필드 추가로 끝납니다(로그표 갱신은 필요). skip 비중이 iOS에서 급감하는지가 이 수정의 직접 지표입니다.

배포 후 확인 3가지

① iOS skip 비중 급감 · ② 복구 성공(recovered=1) 건수가 recover=hit 건수와 일치(불일치분 = 서버 등록 실패) · ③ 성공/실패 로그가 생성 1회당 1건인지(이중 기록 회귀 확인).

복구 로직이 없는 프로젝트(마종)에 새로 넣는 건 보류

복구 성공이 아직 실측되지 않았고, 넣으면 실패 경로에 네트워크 왕복(getTournamentsAsync)이 하나 늘어 결과창 흐름이 그만큼 지연됩니다. 계측이 붙은 프로젝트에서 recover=hit이 실제로 나오는 것을 확인한 다음에 판단하는 편이 안전합니다.

확인 범위 지점 목록은 각 리포 main 브랜치에서 An unexpected error occurred 문자열을 전수 검색한 2026-08-20 시점 실측입니다(라인 번호는 그 시점 기준). 건수 근거 솔리테어 08-14~17 3120_TOURNAMENT_CREATE_FAIL의 error_message 기준이며, 다른 프로젝트의 iOS 누락 규모는 측정하지 않았습니다 — 코드가 동일하므로 같은 성격의 누락이 있다는 것까지가 확인된 범위입니다. 솔리테어 결과 빌드 458에서 못 살린 건 0 · 문구 불일치 폐기 0. 단 456에서도 못 살린 건이 0이었으므로 개선 폭 자체는 이 지표로 증명되지 않습니다.
