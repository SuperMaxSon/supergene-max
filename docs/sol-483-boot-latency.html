Q1 — 부팅 24단계 도달 시각 (485+ · 483~484 · 477이하) 
-- 위 두 곡선을 그대로 3군으로 확장한 쿼리.
-- 결과를 (구분, 로그, 빌드군) 순으로 받아 D 객체의 3원소 배열에 그대로 밀어 넣는다.
-- ⚠ 기간 = 아래 WHERE 의 날짜 두 개. 지금 창(09-02~09-03)에 485가 이미 소량 잡힌다(NRU 72세션).
--    표본이 쌓이면 창을 뒤로 옮긴다. 미래 날짜를 넣으면 0 B / 0행이 나온다.
-- 600000 = 10분, 넘는 값은 이상치로 버린다.
WITH src AS (
    SELECT
        CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS sk,
        CASE
            WHEN client_version >= 485              THEN '485+'
            WHEN client_version BETWEEN 483 AND 484 THEN '483~484'
            WHEN client_version <= 477              THEN '477-'
        END                                        AS grp,
        IF(logincount_total <= 1, 'NRU', 'RU')     AS seg,
        event,
        CAST(JSON_VALUE(data, '$.time') AS INT64)  AS t,
        log_time
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-09-02' AND '2026-09-03'
      AND (is_dev = FALSE OR is_dev IS NULL)
      AND player_id > 0
      AND logincount_total IS NOT NULL
      AND JSON_VALUE(data, '$.time') IS NOT NULL
      AND event IN (
          'INTRO_DEBUG_STAGE_MAPS', 'INTRO_BUNDLE', 'INTRO_SIGNED_PLAYER_INFO',
          'INTRO_FB_FRIEND', 'INTRO_FB_ENTRY_POINT', 'INTRO_FB_SUBSCRIBE_BOT',
          'INTRO_GAME_DATA', 'INTRO_FB_SUBSCRIBE_BOT_FINISH', 'INTRO_OBJECT_POOL',
          'INTRO_BUNDLE_FINISH', 'INTRO_SIGNED_PLAYER_INFO_FINISH', 'INTRO_DEBUG_FB_DATA',
          'INTRO_OBJECT_POOL_FINISH', 'INTRO_FB_ENTRY_POINT_FINISH', 'INTRO_FB_ENTRY_DATA',
          'INTRO_FB_ENTRY_DATA_FINISH', 'INTRO_DEBUG_FB_DATA_FINISH', 'INTRO_GAME_DATA_FINISH',
          'INTRO_DEBUG_STAGE_MAPS_FINISH', 'INTRO_FB_FRIEND_FINISH', 'INTRO_LOGIN',
          'INTRO_DEBUG_LOGIN_FINISH', '1000_LOGIN_COMPLETE', '1010_LOAD_COMPLETE'
      )
),
one AS (        -- 한 세션에서 같은 로그가 두 번 찍히면 첫 번째만 남긴다
    SELECT * FROM src
    WHERE grp IS NOT NULL AND t BETWEEN 0 AND 600000
    QUALIFY ROW_NUMBER() OVER (PARTITION BY sk, event ORDER BY log_time, t) = 1
),
done AS (       -- 완주 세션만. 중간 이탈은 Q2에서 따로 본다
    SELECT DISTINCT sk FROM one WHERE event = '1010_LOAD_COMPLETE'
),
f AS (
    SELECT o.* FROM one o JOIN done USING (sk)
)
SELECT
    seg                                    AS `구분`,
    event                                  AS `로그`,
    grp                                    AS `빌드군`,
    COUNT(DISTINCT sk)                     AS `세션`,
    CAST(ROUND(AVG(t)) AS INT64)           AS `평균_ms`,
    APPROX_QUANTILES(t, 100)[OFFSET(50)]   AS `p50_ms`,
    APPROX_QUANTILES(t, 100)[OFFSET(90)]   AS `p90_ms`
FROM f
GROUP BY 1, 2, 3
ORDER BY `구분`, `로그`, `빌드군`
Q2 — 단계 도달률 (중간 이탈 판정 · Q1과 반드시 짝으로) 
-- Q1이 완주 세션만 보기 때문에 반드시 짝으로 돌려야 하는 쿼리다.
-- 용량이 줄면 느린 회선에서 끝까지 오는 사람 자체가 늘고, 그러면 느린 세션이
-- 표본에 다시 들어와 Q1의 p90은 오히려 나빠 보일 수 있다. 그때 판정은 이 쿼리가 한다.
-- ⚠ 기간 = 아래 WHERE 의 날짜 두 개. 지금 창(09-02~09-03)으로 바로 돌아간다.
--    485 배포 후에는 배포 다음 날 ~ +3일로 옮긴다. 미래 날짜 = 0 B / 0행.
WITH src AS (
    SELECT
        CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS sk,
        CASE
            WHEN client_version >= 485              THEN '485+'
            WHEN client_version BETWEEN 483 AND 484 THEN '483~484'
            WHEN client_version <= 477              THEN '477-'
        END                                        AS grp,
        IF(logincount_total <= 1, 'NRU', 'RU')     AS seg,
        event
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-09-02' AND '2026-09-03'
      AND (is_dev = FALSE OR is_dev IS NULL)
      AND player_id > 0
      AND logincount_total IS NOT NULL
      AND event IN ('INTRO_BUNDLE', 'INTRO_BUNDLE_FINISH', 'INTRO_LOGIN',
                    '1000_LOGIN_COMPLETE', '1010_LOAD_COMPLETE')
),
s AS (
    SELECT
        sk, grp, seg,
        LOGICAL_OR(event = 'INTRO_BUNDLE')        AS hit_bundle,
        LOGICAL_OR(event = 'INTRO_BUNDLE_FINISH') AS hit_bundle_fin,
        LOGICAL_OR(event = 'INTRO_LOGIN')         AS hit_login,
        LOGICAL_OR(event = '1000_LOGIN_COMPLETE') AS hit_login_done,
        LOGICAL_OR(event = '1010_LOAD_COMPLETE')  AS hit_load_done
    FROM src
    WHERE grp IS NOT NULL
    GROUP BY 1, 2, 3
)
SELECT
    seg                 AS `구분`,
    grp                 AS `빌드군`,
    COUNTIF(hit_bundle) AS `인트로_진입_세션`,
    ROUND(COUNTIF(hit_bundle AND hit_bundle_fin) / NULLIF(COUNTIF(hit_bundle), 0) * 100, 2) AS `번들완료_도달_pct`,
    ROUND(COUNTIF(hit_bundle AND hit_login)      / NULLIF(COUNTIF(hit_bundle), 0) * 100, 2) AS `로그인시작_도달_pct`,
    ROUND(COUNTIF(hit_bundle AND hit_login_done) / NULLIF(COUNTIF(hit_bundle), 0) * 100, 2) AS `로그인완료_도달_pct`,
    ROUND(COUNTIF(hit_bundle AND hit_load_done)  / NULLIF(COUNTIF(hit_bundle), 0) * 100, 2) AS `로드완료_도달_pct`
FROM s
GROUP BY 1, 2
ORDER BY `구분`, `빌드군`
Q3 — main.js 부트 구간 절대값 (485 단독 · 483과 지연 비교는 불가) 
-- ⚠ 이 쿼리는 485 단독이다. main.js 로그에 data.time 이 들어간 건 2026-09-02 커밋부터라
--    483 이하의 main.js 로그에는 time 필드 자체가 없다(코드 실측). 지연 비교는 485부터 가능.
--    483과의 대조는 Q3b(건수 비율)로 한다.
-- FIRST_LOG · INTRO_FB_START 는 FBInstant 초기화 전에 찍혀 플레이어 ID가 '-1'이다.
-- 세션 조인도, logincount_total 기반 NRU 판정도 못 쓴다. 그래서 이 쿼리만
--   · 버전을 테이블 컬럼이 아니라 data.client_version 에서 꺼내고
--   · 신규 여부를 data.isNewDevice (main.js가 직접 싣는 값)로 가르고
--   · 세션이 아니라 로그 단위 분포로 낸다.
-- ALL_* 는 tryLog() 가 기기 접미사 붙은 로그와 함께 접미사 없이 한 번 더 보내는 집계용이다.
-- ⚠ 이 쿼리는 client_version >= 485 만 본다. 표본이 아직 작다(09-02~03 NRU 72세션).
--    기간 = 아래 WHERE 의 날짜 두 개. 배포 후 배포 다음 날 ~ +3일로 옮긴다.
-- 600000 = 10분 이상치 컷.
WITH src AS (
    SELECT
        IF(LOWER(JSON_VALUE(data, '$.isNewDevice')) = 'true', '신규기기', '재방문기기') AS seg,
        event,
        CAST(JSON_VALUE(data, '$.time') AS INT64) AS t
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-09-02' AND '2026-09-03'
      AND (is_dev = FALSE OR is_dev IS NULL)
      AND JSON_VALUE(data, '$.time') IS NOT NULL
      AND CAST(JSON_VALUE(data, '$.client_version') AS INT64) >= 485
      AND event IN (
          'FIRST_LOG',              -- main.js 진입
          'INTRO_FB_START',         -- FBInstant.initializeAsync 호출 직전
          'INTRO_FB_START_FINISH',  -- initializeAsync 완료
          'ALL_LOAD_FB',            -- getEntryPointAsync 완료 = FB 준비 끝
          'ALL_LOAD_INTRO',         -- ★ preloadSceneAsync(launchScene) 완료 = 인트로 씬 다운로드+파싱 끝
          'ALL_LOAD_INTRO_START',   -- runSceneImmediate 시작
          'ALL_LOAD_INTRO_FINISH'   -- 씬 전환 완료
      )
)
SELECT
    seg                                    AS `기기`,
    event                                  AS `로그`,
    COUNT(*)                               AS `로그수`,
    CAST(ROUND(AVG(t)) AS INT64)           AS `평균_ms`,
    APPROX_QUANTILES(t, 100)[OFFSET(50)]   AS `p50_ms`,
    APPROX_QUANTILES(t, 100)[OFFSET(90)]   AS `p90_ms`
FROM src
WHERE t BETWEEN 0 AND 600000
GROUP BY 1, 2
ORDER BY `기기`, `p50_ms`
Q3b — main.js 부트 도달률 (483 vs 485 · 시간 필드 없이 비교) 
-- 483에는 data.time 이 없지만 로그 행 자체는 2026-01-08부터 쌓여 있다(코드 실측).
-- 그래서 지연 대신 "몇 %가 다음 단계까지 왔나"로 두 빌드를 비교한다.
-- 용량이 줄면 ALL_LOAD_INTRO 도달률이 올라가야 한다 — 여기가 다운로드 비용이 실리는 지점이다.
-- 분모는 FIRST_LOG = main.js 가 실행된 모든 브라우저.
-- ⚠ 기간 = 아래 WHERE 의 날짜 두 개. 지금 창(09-02~09-03)으로 바로 돌아간다.
--    485 배포 후에는 배포 다음 날 ~ +3일로 옮긴다. 미래 날짜 = 0 B / 0행.
WITH src AS (
    SELECT
        CASE
            WHEN CAST(JSON_VALUE(data, '$.client_version') AS INT64) >= 485              THEN '485+'
            WHEN CAST(JSON_VALUE(data, '$.client_version') AS INT64) BETWEEN 483 AND 484 THEN '483~484'
            WHEN CAST(JSON_VALUE(data, '$.client_version') AS INT64) <= 477              THEN '477-'
        END                                       AS grp,
        IF(LOWER(JSON_VALUE(data, '$.isNewDevice')) = 'true', '신규기기', '재방문기기') AS seg,
        event
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-09-02' AND '2026-09-03'
      AND (is_dev = FALSE OR is_dev IS NULL)
      AND JSON_VALUE(data, '$.client_version') IS NOT NULL
      AND event IN ('FIRST_LOG', 'INTRO_FB_START', 'INTRO_FB_START_FINISH',
                    'ALL_LOAD_FB', 'ALL_LOAD_INTRO', 'ALL_LOAD_INTRO_FINISH')
),
s AS (
    SELECT
        grp, seg,
        COUNTIF(event = 'FIRST_LOG')             AS first_log,
        COUNTIF(event = 'INTRO_FB_START_FINISH') AS fb_init_done,
        COUNTIF(event = 'ALL_LOAD_FB')           AS fb_ready,
        COUNTIF(event = 'ALL_LOAD_INTRO')        AS intro_loaded,
        COUNTIF(event = 'ALL_LOAD_INTRO_FINISH') AS intro_shown
    FROM src
    WHERE grp IS NOT NULL
    GROUP BY 1, 2
)
SELECT
    seg                                                     AS `기기`,
    grp                                                     AS `빌드군`,
    first_log                                               AS `FIRST_LOG`,
    ROUND(fb_init_done / NULLIF(first_log, 0) * 100, 2)     AS `FB초기화완료_pct`,
    ROUND(fb_ready     / NULLIF(first_log, 0) * 100, 2)     AS `FB준비완료_pct`,
    ROUND(intro_loaded / NULLIF(first_log, 0) * 100, 2)     AS `인트로씬로드_pct`,
    ROUND(intro_shown  / NULLIF(first_log, 0) * 100, 2)     AS `인트로씬표시_pct`
FROM s
ORDER BY `기기`, `빌드군`
Q4 — 실패 · 이탈 로그 발생률 (485 신설 로그 · 회귀 감시) 
-- 용량을 줄이는 수단은 텍스처 양자화와 모듈 제거다. 둘 다 "덜 받아서 빨라진다"와
-- "빠진 게 있어서 안 뜬다"가 같은 변경에서 나온다. 이 쿼리가 그 뒷면을 본다.
-- 분모는 FIRST_LOG = 부팅을 시도한 모든 브라우저.
-- 아래 이탈·실패 로그는 2026-09-02 신설이라 483에는 없다 — 절대값으로만 판정한다.
-- ⚠ 기간 = 아래 WHERE 의 날짜 두 개. 지금 창(09-02~09-03)으로 바로 돌아간다.
--    485 배포 후에는 배포 다음 날 ~ +3일로 옮긴다. 미래 날짜 = 0 B / 0행.
WITH src AS (
    SELECT
        CAST(JSON_VALUE(data, '$.client_version') AS INT64) AS ver,
        event
    FROM `game-log-359704.raw.solitaire_city_journey`
    WHERE log_date BETWEEN '2026-09-02' AND '2026-09-03'
      AND (is_dev = FALSE OR is_dev IS NULL)
      AND JSON_VALUE(data, '$.client_version') IS NOT NULL
      AND event IN (
          'FIRST_LOG',
          'INTRO_SCRIPT_LOAD_FAIL',       -- 엔진 스크립트 자체를 못 받음
          'INTRO_ENGINE_ABANDON',         -- 엔진 로드 중 창을 닫음
          'INTRO_FB_ABANDON',             -- FB init 중 창을 닫음
          'INTRO_FB_ABANDON_AFTER_FAIL',  -- FB init 실패 후 창을 닫음
          'INTRO_FB_START_FAIL',
          'INTRO_FB_AFTER_INIT_ERROR'
      )
),
s AS (
    SELECT
        IF(ver >= 485, '485+', '484-')                 AS grp,
        COUNTIF(event = 'FIRST_LOG')                   AS first_log,
        COUNTIF(event = 'INTRO_SCRIPT_LOAD_FAIL')      AS script_fail,
        COUNTIF(event = 'INTRO_ENGINE_ABANDON')        AS engine_abandon,
        COUNTIF(event = 'INTRO_FB_ABANDON')            AS fb_abandon,
        COUNTIF(event = 'INTRO_FB_ABANDON_AFTER_FAIL') AS fb_abandon_fail,
        COUNTIF(event = 'INTRO_FB_START_FAIL')         AS fb_start_fail,
        COUNTIF(event = 'INTRO_FB_AFTER_INIT_ERROR')   AS fb_init_error
    FROM src
    GROUP BY 1
)
SELECT
    grp                                                    AS `빌드군`,
    first_log                                              AS `FIRST_LOG`,
    ROUND(script_fail     / NULLIF(first_log, 0) * 100, 3) AS `스크립트로드실패_pct`,
    ROUND(engine_abandon  / NULLIF(first_log, 0) * 100, 3) AS `엔진로드중이탈_pct`,
    ROUND(fb_abandon      / NULLIF(first_log, 0) * 100, 3) AS `FB초기화중이탈_pct`,
    ROUND(fb_abandon_fail / NULLIF(first_log, 0) * 100, 3) AS `FB실패후이탈_pct`,
    ROUND(fb_start_fail   / NULLIF(first_log, 0) * 100, 3) AS `FB초기화실패_pct`,
    ROUND(fb_init_error   / NULLIF(first_log, 0) * 100, 3) AS `FB초기화후에러_pct`
FROM s
ORDER BY `빌드군` DESC
전제와 한계 버전 경계 485+ / 483~484 / 477이하는 가정입니다 — 484가 실제로 배포됐는지, 485가 최종 빌드 번호가 맞는지를 Q0로 먼저 확인하고 나머지 쿼리의 CASE를 함께 고쳐야 합니다. NRU 판정을 logincount_total <= 1로 잡은 것은 위 곡선의 = 1보다 넓은 조건이라 0이 섞인 세션까지 들어옵니다(허브의 다른 로딩 문서와 맞춘 조건) — 483 수치를 재산출해 함께 갈아 끼우는 이유입니다. Q1·Q2는 같은 기간에 세 빌드가 공존한다는 전제입니다. 485가 100% 롤아웃되어 483 트래픽이 말라붙으면 483 열은 배포 직전 기간을 따로 잡아 뽑아야 하고, 그때는 기기·회선 구성이 달라진다는 걸 감안해야 합니다. 모든 쿼리에 country 필터가 없습니다 — 두 기간의 국가 구성이 크게 다르면 용량 효과와 구분이 안 되므로, Q0에서 구성이 흔들려 보이면 country = 'US'를 추가해 다시 돌립니다. data 스캔은 비용이 크므로 기간은 3~4일을 넘기지 않습니다.
