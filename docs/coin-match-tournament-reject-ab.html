잔존은 아직 근거가 되지 못합니다

사전집계 테이블 기준으로 55쌍 중 B 24 : A 31, 부호검정 p≈0.419 로 어느 쪽으로도 기울지 않았습니다. B가 높은 구간은 D+4~D+7 넷뿐입니다. 처치를 실제로 받은 유저가 코호트의 2% 남짓이라 희석이 크지만, 그 층만 떼어 본 이전 수치는 오염된 NRU 위에서 계산돼 폐기했습니다 — 잔존 판정에 정정 내역과 재계산 방법을 정리했습니다.

KPI 보드 막대 길이는 같은 단위 계열 안에서만 비교됩니다

빌드 교란은 없지만 두 가지는 남습니다. ① 같은 기간 구버전 3366 이 8/29까지 44,325명에게 서빙됐고 두 군 어디에도 들어가지 않습니다 — A/B 내부 비교에는 문제없지만 전체 유저의 그림은 아닙니다. ② 처치와 무관한 컨텍스트 전환 성공률이 1.46%p 벌어졌습니다. 코드가 같으니 빌드로는 설명되지 않고, 이 폭이 곧 노이즈 하한선입니다 — 그보다 작은 Δ 는 판정 근거가 되지 못합니다.

v1.9 이전의 잔존 수치는 폐기했습니다

이전 판본은 raw 에서 최근 69일 안에 첫 로그인인 유저를 NRU 로 잡았습니다. 그보다 오래 쉬었다 돌아온 유저가 신규로 섞여 코호트가 27~31% 부풀었고, 복귀 유저는 잔존이 높아 전체 잔존율도 함께 올라가 있었습니다(08-27 D+1 8.54% → 실제 6.19%). 지금은 팀 표준 사전집계 테이블 stat.coin_match_prod_nru_retention3 를 씁니다. 그 결과 방향이 뒤집혔습니다 — B 우세(38:28)로 보이던 것이 실제로는 A 쪽(24:31)입니다.

그래도 결론은 같습니다 — 무승부

10개 구간 중 B가 높은 구간은 4개(D+4~D+7)이고 나머지는 A가 높습니다. 코호트 쌍으로 세면 55쌍 중 B 24 : A 31, 부호검정 p≈0.419 로 어느 쪽으로도 기울었다고 말할 수 없습니다. p<.05 인 칸은 D+10 하나뿐인데(p=0.032) 08-27 코호트 4,149명 단독이라 40명 대 24명 차이이고, 55번 검정하면 우연히 2.8칸이 나오는 자리입니다.

처치 노출 층 분석은 다시 해야 합니다

"처치 층 D+7 +19.4%" 는 같은 오염된 NRU 위에서 계산된 값이라 지금은 신뢰할 수 없습니다. 층 구분(설치 당일 연속 3회 거절 도달)은 stat 에 없는 우리 실험 전용 축이므로, 해당 player_id 목록을 raw 에서 한 번만 뽑아 중간 테이블로 굳힌 뒤 stat 코호트와 조인해 재계산해야 합니다 — 쿼리는 아래에 있습니다.

잔존 코호트 격자 D+N 리텐션 — 정확히 N일 뒤 그날 접속 · 붙어 있는 3374·3375 쌍 안에서 세로로만 견주세요

그 코호트·그 날짜에서 더 높은 쪽 · 진할수록 격차가 큼(0.5%p에서 최대) 출처 stat.coin_match_prod_nru_retention3 · raw 스캔 0 · = 아직 안 온 날 유의성 표시는 두지 않았습니다 — 66번 검정이라 보정하면 통과 칸이 0개입니다 (p 값은 칸에 올리면 나옵니다)
숫자는 그 코호트가 정확히 N일 뒤 그날 다시 접속한 비율(%)입니다 — 업계에서 말하는 D1 / D3 / D7 리텐션과 같은 정의입니다. 누적이 아니라 그날 하루 출석률이라 보통은 내려가지만 단조 감소가 보장되지는 않습니다 — 하루 건너뛰고 이틀 뒤에 온 유저는 D+2에서 빠지고 D+3에 잡히기 때문입니다. 실제로 08-27 코호트 A는 D+6 → D+7 에서 올라갑니다(1.28% → 1.69%). · 로 찍힌 칸은 아직 그 날짜가 오지 않은 것이고, 그래서 표가 아래로 갈수록 짧아집니다. 비교는 붙어 있는 A·B 한 쌍 안에서 세로로만 하세요 — 다른 코호트일끼리 가로로 이어 읽으면 안 됩니다. 08-27은 롤아웃 첫날이라 조기 업데이트 유저만 잡혀 코호트가 4천명대로 작습니다 — 이 행의 뒤쪽 칸이 가장 많이 흔들립니다. D+11~D+14 는 전 칸이 '·' 입니다 — stat 이 하루 지연 갱신이라 오늘(9/7) 기준 08-27 코호트도 D+10 까지만 차 있습니다.
방향 쏠림이 없습니다

값이 찬 55쌍 중 B가 높은 칸이 24, A가 높은 칸이 31 로 부호검정 p≈0.419 입니다. 개별 p<.05 인 칸은 08-27 D+10 하나(A 0.96% ↔ B 0.56%, p=0.032)인데 4,149명 코호트에서 40명 대 24명 차이라, 55번 검정하면 우연히 2.8칸이 나오는 자리입니다.

출처가 raw 에서 stat 으로 바뀌었습니다

stat.coin_match_prod_nru_retention3 의 join_date × client_version 을 그대로 씁니다 — raw 스캔 0. 이전 판본의 raw 직접 집계는 NRU 정의가 느슨해 코호트가 27~31% 부풀어 있었고, 그 수치는 폐기했습니다. D+11 이후가 전부 비어 있는 것은 stat 이 하루 지연 갱신이라 오늘(9/7) 시점에 08-27 코호트가 D+10 까지만 채워졌기 때문입니다.

단일 쿼리 — 지표를 행, A/B를 열로 피벗 
WITH base AS (
    SELECT
        CASE WHEN client_version = 3375 THEN 'B' ELSE 'A' END AS ab_group,
        player_id,
        CONCAT(CAST(player_id AS STRING), '_', CAST(logincount_total AS STRING)) AS session_key,
        event
    FROM `game-log-359704.raw.coin_match`
    WHERE log_date BETWEEN '2026-08-27' AND '2026-09-07'
      AND client_version IN (3374, 3375, 3376, 3377, 3378)
),
core AS (
    SELECT
        ab_group,
        COUNT(DISTINCT CASE WHEN event = '1000_LOGIN_COMPLETE' THEN player_id END) AS users,
        COUNT(DISTINCT CASE WHEN event = '1000_LOGIN_COMPLETE' THEN session_key END) AS sessions,
        COUNTIF(event = '2100_GAMEPLAY_START') AS play_starts,
        COUNTIF(event = '2300_GAMEPLAY_FINISH') AS play_finishes,
        COUNT(DISTINCT CASE WHEN event = '1170_PLAYTIME_300S' THEN session_key END) AS sessions_300s,
        COUNTIF(event = '3100_TOURNAMENT_CREATE') AS tc_try,
        COUNTIF(event = '3110_TOURNAMENT_CREATE_SUCCESS') AS tc_success,
        COUNTIF(event = '3130_TOURNAMENT_CREATE_SUPPRESSED') AS tc_suppressed,
        COUNTIF(event = '3200_TOURNAMENT_SHARE') AS ts_try,
        COUNTIF(event = '3210_TOURNAMENT_SHARE_SUCCESS') AS ts_success,
        COUNTIF(event = '3400_MSG_P2P') AS p2p_try,
        COUNTIF(event = '3410_MSG_P2P_SUCCESS') AS p2p_success,
        COUNTIF(event = '3500_FEED_SHARE') AS feed_try,
        COUNTIF(event = '3510_FEED_SHARE_SUCCESS') AS feed_success,
        COUNTIF(event = '3000_SWITCH_CONTEXT_START') AS sc_try,
        COUNTIF(event = '3010_SWITCH_CONTEXT_SUCCESS') AS sc_success
    FROM base
    GROUP BY ab_group
),
first_seen AS (
    SELECT player_id, MIN(log_date) AS install_date
    FROM `game-log-359704.raw.coin_match`
    WHERE log_date BETWEEN '2026-07-01' AND '2026-09-07'
      AND event = '1000_LOGIN_COMPLETE'
    GROUP BY player_id
),
nru_group AS (
    SELECT
        f.player_id,
        f.install_date,
        CASE WHEN MIN(l.client_version) = 3375 THEN 'B' ELSE 'A' END AS ab_group
    FROM first_seen f
    JOIN `game-log-359704.raw.coin_match` l
      ON l.player_id = f.player_id
     AND l.log_date = f.install_date
    WHERE f.install_date BETWEEN '2026-08-27' AND '2026-08-31'
      AND l.log_date BETWEEN '2026-08-27' AND '2026-08-31'
      AND l.event = '1000_LOGIN_COMPLETE'
      AND l.client_version IN (3374, 3375, 3376, 3377, 3378)
    GROUP BY f.player_id, f.install_date
),
activity AS (
    SELECT DISTINCT player_id, log_date
    FROM `game-log-359704.raw.coin_match`
    WHERE log_date BETWEEN '2026-08-27' AND '2026-09-07'
      AND event = '1000_LOGIN_COMPLETE'
),
retention AS (
    SELECT
        g.ab_group,
        COUNT(DISTINCT g.player_id) AS cohort_size,
        COUNT(DISTINCT CASE WHEN DATE_DIFF(a.log_date, g.install_date, DAY) = 1 THEN g.player_id END) AS d1,
        COUNT(DISTINCT CASE WHEN DATE_DIFF(a.log_date, g.install_date, DAY) = 7 THEN g.player_id END) AS d7
    FROM nru_group g
    LEFT JOIN activity a
      ON a.player_id = g.player_id
    GROUP BY g.ab_group
),
metrics AS (
    SELECT 1 AS sort_key, 'users' AS metric, ab_group, CAST(users AS FLOAT64) AS value FROM core
    UNION ALL SELECT 2, 'sessions', ab_group, CAST(sessions AS FLOAT64) FROM core
    UNION ALL SELECT 3, 'plays_per_user', ab_group, SAFE_DIVIDE(play_starts, users) FROM core
    UNION ALL SELECT 4, 'plays_per_session', ab_group, SAFE_DIVIDE(play_starts, sessions) FROM core
    UNION ALL SELECT 5, 'finish_rate_pct', ab_group, SAFE_DIVIDE(play_finishes, play_starts) * 100 FROM core
    UNION ALL SELECT 6, 'session_300s_pct', ab_group, SAFE_DIVIDE(sessions_300s, sessions) * 100 FROM core
    UNION ALL SELECT 7, 'nru_cohort_size', ab_group, CAST(cohort_size AS FLOAT64) FROM retention
    UNION ALL SELECT 8, 'd1_retention_pct', ab_group, SAFE_DIVIDE(d1, cohort_size) * 100 FROM retention
    UNION ALL SELECT 9, 'd7_retention_pct', ab_group, SAFE_DIVIDE(d7, cohort_size) * 100 FROM retention
    UNION ALL SELECT 10, 'tournament_create_try_per_user', ab_group, SAFE_DIVIDE(tc_try, users) FROM core
    UNION ALL SELECT 11, 'tournament_create_success_rate_pct', ab_group, SAFE_DIVIDE(tc_success, tc_try) * 100 FROM core
    UNION ALL SELECT 12, 'tournament_suppressed_per_user', ab_group, SAFE_DIVIDE(tc_suppressed, users) FROM core
    UNION ALL SELECT 13, 'tournament_share_success_rate_pct', ab_group, SAFE_DIVIDE(ts_success, ts_try) * 100 FROM core
    UNION ALL SELECT 14, 'msg_p2p_try_per_user', ab_group, SAFE_DIVIDE(p2p_try, users) FROM core
    UNION ALL SELECT 15, 'msg_p2p_success_rate_pct', ab_group, SAFE_DIVIDE(p2p_success, p2p_try) * 100 FROM core
    UNION ALL SELECT 16, 'feed_share_try_per_user', ab_group, SAFE_DIVIDE(feed_try, users) FROM core
    UNION ALL SELECT 17, 'feed_share_success_rate_pct', ab_group, SAFE_DIVIDE(feed_success, feed_try) * 100 FROM core
    UNION ALL SELECT 18, 'switch_context_success_rate_pct', ab_group, SAFE_DIVIDE(sc_success, sc_try) * 100 FROM core
),
pivoted AS (
    SELECT
        sort_key,
        metric,
        MAX(IF(ab_group = 'A', value, NULL)) AS group_a,
        MAX(IF(ab_group = 'B', value, NULL)) AS group_b
    FROM metrics
    GROUP BY sort_key, metric
)
SELECT
    metric,
    ROUND(group_a, 2) AS group_a,
    ROUND(group_b, 2) AS group_b,
    ROUND(group_b - group_a, 2) AS diff,
    ROUND(SAFE_DIVIDE(group_b - group_a, group_a) * 100, 1) AS diff_pct
FROM pivoted
ORDER BY sort_key

처치 노출 층 — raw 를 한 번만 읽어 중간 테이블로 굳히는 쿼리
층 구분(설치 당일 연속 3회 거절 도달)은 이 실험 전용 축이라 stat 에 없습니다. 대신 player_id 목록 하나면 되므로 12 파티션-일 · 1회만 읽어 테이블로 저장하고, 이후 재분석은 이 테이블과 stat 을 조인해 raw 를 다시 읽지 않습니다. 
CREATE OR REPLACE TABLE `game-log-359704.<내_데이터셋>.coin_match_ab_treated` AS
WITH base AS (
    SELECT player_id, log_date, log_time, logincount_total, event,
           JSON_VALUE(data, '$.error_code') AS error_code
    FROM `game-log-359704.raw.coin_match`
    WHERE log_date BETWEEN '2026-08-27' AND '2026-09-06'
      AND event IN ('3110_TOURNAMENT_CREATE_SUCCESS', '3120_TOURNAMENT_CREATE_FAIL')
),
-- 성공이 나올 때마다 streak_group 이 올라가 '연속' 구간이 끊긴다
-- (클라이언트가 생성 성공 시 카운터를 0 으로 되돌리는 것과 같은 규칙).
streak AS (
    SELECT player_id, log_date, logincount_total, event, error_code,
           SUM(CASE WHEN event = '3110_TOURNAMENT_CREATE_SUCCESS' THEN 1 ELSE 0 END)
               OVER (PARTITION BY player_id, logincount_total ORDER BY log_time
                     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS streak_group
    FROM base
),
runs AS (
    SELECT player_id, log_date, COUNT(*) AS rej
    FROM streak
    WHERE event = '3120_TOURNAMENT_CREATE_FAIL' AND error_code = 'USER_INPUT'
    GROUP BY player_id, log_date, logincount_total, streak_group
)
SELECT player_id, MIN(log_date) AS first_reached_date
FROM runs
WHERE rej >= 3
GROUP BY player_id
재계산이 필요합니다. 문서에 남아 있는 층별 수치(처치 층 D+7 +19.4% 등)는 폐기된 raw NRU 위에서 계산된 값입니다. 이 테이블을 만든 뒤 stat 코호트와 조인해 다시 뽑아야 합니다 — 다만 stat 은 코호트 집계라 개인 단위 조인이 불가능하므로, 층별 잔존은 이 목록으로 raw 를 한 번 더 읽거나 층을 포함한 전용 집계 테이블을 따로 만들어야 합니다.
raw 스캔 비용에 대해 이 문서의 쿼리는 raw.coin_match 를 직접 읽습니다. 과거 날짜 집계를 반복 실행하지 마십시오 — raw 는 한 번 쌓인 행이 바뀌지 않으므로 같은 기간을 다시 계산할 이유가 없고, 결과를 중간 집계 테이블에 한 번 저장해 재사용하는 편이 맞습니다. 팀에 stat 사전집계 데이터셋(주요 이벤트 횟수·리텐션)이 있으므로, 정기 갱신은 그쪽으로 옮기는 것이 원칙입니다 — 이 문서의 쿼리는 A/B 군 배정(설치일 client_version)과 처치 노출 층(설치 당일 연속 거절 3회)이 stat 에 있는지 확인되기 전까지의 임시판입니다.
확인 범위 A/B 구분자는 client_version 뿐입니다 — 페이스북이 어느 호스팅을 서빙했는지로 갈립니다. 기간 내 버전 분포는 3374 224,799명 · 3375 224,297명 · 3366 44,325명이고 나머지(3162·3363·3370·3372·3373·3377·3378)는 전부 합쳐 15명 이하라 무시했습니다. 보드 수치는 지표 쿼리 1회분이고 이 분포는 이후 조회분이라, 유저 수가 양쪽 모두 209명씩 더 잡혀 있습니다. 생성 성공 / 유저 행은 쿼리 결과가 아니라 tournament_create_try_per_user × tournament_create_success_rate_pct 로 계산한 파생값이라, 반올림된 두 값의 곱이라는 오차가 있습니다. 유의성은 두 비율 검정(pooled z)이며, 분모를 _per_user × users 로 역산했으므로 역시 반올림 오차를 포함합니다. 비율이 아닌 행(판수 등)은 검정하지 않았습니다.
