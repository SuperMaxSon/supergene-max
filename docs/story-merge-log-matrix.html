등록 방식이 왜 중요한가

스토리 머지는 솔리테어 계열의 레지스트리 방식을 상속받았습니다. 즉 LogType enum(≈110개)은 이미 있고 registLogEvent(LogType.X, "0000_NAME") 매핑만 비어 있습니다. 문자열 직접 방식(코지·코인·마종·블블)과 달리 이벤트명 매핑 한 곳만 채우면 기존 콜사이트가 전부 살아납니다. 이것이 아래 "즉시 가능" 판정이 나오는 근거입니다.

이 표를 읽는 법

게임 5칸은 "그 게임이 이 계열을 갖고 있나"만 표시합니다 — 이름·코드가 게임마다 조금씩 다르므로 계열 단위로 묶었습니다. 판정의 핵심은 마지막 머지 칸이고, 근거는 항상 호출부가 존재하는가입니다. 스크립트가 리포에 있어도 프리팹이 없으면 도달 불가 = ❌ 또는 🔶로 봤습니다 (ViewManager.load 가 실패하기 때문). 이 구분이 중요한 이유는, 🔶 중 상당수가 프리팹 하나만 만들면 그날 ✅ 로 바뀌는 것이라 작업량 견적이 완전히 다르기 때문입니다.

열 색은 프로젝트 식별색입니다 — 판정 열이 6개라 색 없이는 행을 따라가다 칸을 잃습니다. 판정 대상인 머지를 맨 앞에 두고 테두리로 강조했고, 나머지 5개는 대조군이라 뒤에 붙였습니다. 즉 3열만 읽으면 결론이고, 4~8열은 그 결론의 근거입니다.

✅ 15계열의 성격 — 대부분 "이미 심겨 있다"

✅ 로 잡힌 것 중 1000 · INTRO_* · 6000 · 6040 · 9000~9300 · 89xx 는 프로토에 이미 BaseLogManager.log() 호출문이 들어가 있습니다 (총 ~25곳). 즉 코드를 새로 쓰는 작업이 아니라 이벤트명 매핑을 채우고 전송 함수를 되살리는 작업입니다. 신규 코드가 필요한 것은 아래 "신규 정의" 섹션뿐입니다.

🔶 2100 / 2300 을 재정의해야 하는 이유

5게임 전부 2100_GAMEPLAY_START / 2300_GAMEPLAY_FINISH 를 스테이지 1판 단위로 씁니다. 스토리 머지에는 스테이지가 없고 11노드 선형 순회 1회가 세션 전부입니다. 그대로 쓰면 세션당 1건씩만 찍혀 퍼널 분석이 안 됩니다. 그래서 2100/2300 은 스토리 러너 시작/완주로 두고, 실제 퍼널은 아래 노드 단위 신규 이벤트로 잡는 것이 맞습니다.

# 막고 있는 것 현재 상태 해야 할 일
1 이벤트명 매핑 공백 LogEventHandler.logEventMap 이 끝까지 비어 있음. FacebookLogEventHandler.initLogEvent() 의 유일한 addLogEvent 가 주석 처리 StoryMergeProtoLogManager.initLogManager() 에서 registLogEvent(LogType.X, "0000_NAME") 등록. 여기만 채우면 기존 ~25개 콜사이트가 그대로 발화
2 전송 함수 무력화 NetworkManager.log() 본문이 "스토리 프로토타입은 로그/통계 페이로드를 수집하거나 전송하지 않는다" 주석 한 줄. loginLog() 는 Promise.resolve(null) POST 복원. 로그 호스트 상수는 살아 있음 — ProjectConfig.SERVER_URL_LOG
3 앱 식별자가 마종을 가리킴 ProjectConfig.ts 가 마종 프로젝트 그대로 (APP_ID_PROD = "mahjong_prod", 마종 CDN 경로) 앱 ID · 서버 경로 교체. 안 하면 마종 로그와 같은 테이블에 섞임
4 플랫폼 인스턴스가 no-op PlatformSelector.platformType 기본값 Preview 이고 이를 바꾸는 코드가 없음 → 실체는 스텁 BasePlatform FB 빌드에서 FaceBookPlatform 선택 경로 확인. 안 되면 getLogHandler() 가 FB 핸들러를 못 줌
1·2 는 실수가 아니라 의도입니다 — 그래서 이건 정책 결정입니다

두 곳 모두 "수집하지 않는다"는 주석이 명시적으로 달려 있습니다. 연출 비교용 프로토라서 통계를 일부러 뺀 것입니다. 즉 버그 수정이 아니라 정책 전환이고, 넣을지부터 정해야 위 매트릭스가 의미를 갖습니다. 넣기로 하면 1·2 자체는 반나절이고, 그 뒤 ✅ 45계열은 신규 코드 0줄로 매핑 등록만 하면 살아납니다. 다만 3번을 빼먹으면 조용히 오염됩니다 — 앱 ID가 mahjong_prod 인 채로 전송이 살아나면 에러 없이 마종 로그 스트림에 섞여 들어가고, 코드값도 겹쳐서 (2100/2300/6040 등) 양쪽 대시보드가 같이 틀어집니다. 1·2보다 3을 먼저 하는 것이 안전합니다.
