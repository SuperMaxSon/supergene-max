검사

스키마는 엔진이 읽는 키와 JSON 컬럼을 맞춰 봅니다 — FAIL 이면 그 컬럼을 안 읽고 돈 것이라 아래 분포 숫자를 믿을 수 없습니다. 규칙은 표본 전량이 기획서 규칙을 지켰는지 봅니다 — 기대값은 엔진이 아니라 시트에서 따로 계산합니다(엔진 계산을 다시 쓰면 같은 착오를 두 번 합니다). 비율은 이항 3σ, 기대빈도 5 미만은 판정에서 뺍니다. PASS 는 「그 항목이 맞다」일 뿐 알고리즘이 정상이라는 뜻이 아닙니다 — 이 페이지가 아예 재지 않는 영역은 「미검증」 표에 적어 뒀습니다. 공용 엔진은 벤치와 같은 파일을 읽습니다 — 갭 3건(가중치 weight×multiple · score_base(coin)·event_id · 누적 난이도 축) 반영, v4.5 에서 시트 셀 메모 대조로 refill_max·반복 감쇠 해석 2건을 정정했습니다. 비율 판정은 동시 비교 개수만큼 임계값을 넓힙니다 — 후보 44종을 각각 3σ 로 재면 엔진이 정상이어도 11% 확률로 하나가 넘어 FAIL 이 뜹니다.
FAIL 엔진과 시트가 어긋남 · 주의 지금은 결과가 같지만 조건이 바뀌면 틀어짐 · PASS 일치 · 필수 우리 판정이 아니라 시트가 매긴 data_manifest.is_critical 값

뽑기 분포

고정 오더는 빼고 랜덤 경로만 연속 발급합니다. 빈 보드면 전 후보가 「미요구」 배수 1000 으로 평평하고, 물건이 쌓이면 「동급·하급 보유」 10000 이 걸려 쏠립니다. 보드는 프리셋입니다 — 시트에 없는 값을 시트 JSON 에 끼우지 않으려고 벤치 보드를 읽지 않습니다. 레일 맥락 — 실제 레일이 없으니 후보 목록에서 표본 3종을 골라 「다른 오더가 요구 중(2종) + 직전 요구(1종)」으로 가정합니다. 그 3종은 후보에서 빠지고, 같은 체인의 다른 단계는 배수 100·1 을 받습니다 — 끄면 배수 4 개 중 이 축 둘이 아예 안 나옵니다. 무엇이 빠졌는지는 아래 줄과 판정 로그 [3] 에 적힙니다. 매 발급 같은 3종이라 결과가 재현됩니다.
