솔리테어 · 코인 매치 플로우 맵과 같은 두 단 구조지만, 축이 다릅니다. 이 프로토는 지면이 4개(intro.fire · ViewStory · ViewMergeBoard · PopupTask)뿐이라 지면 오픈맵을 그대로 옮기면 빈 맵이 됩니다. 정보가 있는 축은 스토리 노드 11개가 연출 모드에 따라 어떻게 소비되는가와 태스크가 머지 1회를 끝낼 때까지 도는 루프입니다. 그래서 맵의 카드를 지면이 아니라 부팅 · 데이터 · 스토리 노드 · 연출 모드 · 태스크 · 시스템 여섯 계층으로 잡았습니다. 1단 오픈맵으로 전체를 훑고, 2단 카드를 누르면 주요 이동 경로 3~5개가 뜹니다 — 지면 카드에는 프리팹을 직접 파싱해 그린 720×1280 세로 와이어프레임이 함께 붙습니다. 전체 버튼과 내부 분기는 그 아래 접힘에 있고 제목에 개수를 적어 뒀습니다. 찾는 게 정해져 있으면 오른쪽 위 검색창(단축키 /)에 메소드 · 노드 · 프리팹 이름을 치면 그 카드를 열고 접힘까지 펼쳐서 보여줍니다. 지면으로 표현되지 않는 두 축은 툴바에서 따로 엽니다 — 노드 표는 노드 11개를 두 빌드에 나란히 놓고 대조한 표 · 태스크 루프 상태 기계 · 데이터 계약이고, 플랫폼 · 빌드는 어댑터 8종과 빌드 프로파일입니다.

왜 축을 바꿨나 — 지면 오픈맵을 그대로 옮기면 빈 맵이 된다

솔리테어는 지면 49개, 코인 매치는 65개였습니다. 이 프로토는 4개입니다. 프리팹은 3장(ViewStory · ViewMergeBoard · PopupTask), cc.Button 은 게임 전체에 5개뿐입니다. 원본 맵의 3단째(버튼 → 호출 사슬)는 세울 근거가 없어 2단으로 접었습니다.

대신 이 프로토에만 있는 축 둘을 카드로 올렸습니다. 연출 모드 3종이 빌드 타임에 갈리는 구조와 태스크 루프입니다. 이 프로젝트의 목적 자체가 “같은 스토리를 채팅 · 스틸컷 · 비디오로 만들어 비교하는 것” 이라, 어느 모드로 빌드했는지가 곧 그 빌드의 정체입니다.

이 그림이 어디서 나왔나

손으로 그린 그림이 아닙니다. assets/bundle/{view,popup} 의 프리팹과 assets/scene/intro.fire 를 파싱해 _trs 좌표와 cc.Widget 정렬을 계산한 결과입니다. 노드 표도 story_node.json 에서 직접 생성했습니다 — 옮겨 적다 틀리는 것을 막기 위해서입니다. 생성기는 이 저장소의 _ignore/flowmap/ 에 있고, 산출물 HTML 은 직접 고치지 않고 조각(parts/)을 고쳐 다시 조립합니다. 회전은 무시했고, 화면 밖 레터박스 채움과 웹 배경은 이름으로 뺐습니다.

비활성 요소는 버리지 않았습니다. 이 프로젝트의 _active=false 는 “에디터 파킹”이 아니라 연출 모드 · 진행도에 따른 런타임 노출이라 그게 곧 지면의 내용입니다. 와이어프레임에 점선으로 남겼습니다. 반복 셀 12개는 대표 1개 + ×n 으로 접었지만, 머지 보드의 6×7 격자 42칸은 접지 않았습니다 — 접으면 한 칸 + ×42 가 되어 그 지면의 정체가 사라지기 때문입니다.

검색 — 접힘 안까지 열어 준다

맵 오른쪽 위 검색창(단축키 / · Ctrl/Cmd+K)에서 923개 항목을 찾습니다. 걸리는 것은 카드 이름(ChatMessageRow · “머지 보드”) · 메소드(waitForIntro) · 프리팹(PopupTask.prefab) · 프리팹 노드 이름(StillcutSurfaceA) · 버튼 라벨입니다. 메소드 설명문까지 같이 뒤지므로 이름이 정확히 기억나지 않아도 걸립니다.

기본 화면이 주요 이동 경로 3~5개로 줄어든 만큼, 상세로 가는 통로는 검색입니다. 고르면 그 카드를 열고, 그 항목이 접힘 안에 있으면 접힘까지 열어 해당 가지를 펼쳐 줍니다.

왜 팩토리가 if 하나 없이 한 줄인가

StoryPresentationFactory.ts 는 지금 new ChatBubbleStoryPresentation(bindings) 한 줄입니다. 런타임 분기로 두면 세 모드의 연출 코드와 에셋이 전부 빌드에 들어갑니다. 프로토의 목적이 연출 비교라 scripts/story-build-profile.js 가 StoryBuildConfig.ts 와 StoryPresentationFactory.ts 두 파일을 통째로 갈아끼웁니다.

그래도 실수로 어긋날 수 있어, StoryNodeRunner.run() 이 만들어진 연출의 getMode() 를 STORY_PRESENTATION_MODE 와 대조하고 다르면 그 자리에서 던집니다. 잘못 조합된 빌드는 첫 노드 전에 죽습니다.

데이터 공유가 절반으로 깨졌다

세 프로파일이 story_node · story_dialogue · present_video 를 공유한다는 원칙은 그대로입니다 (validateProfile() 이 목록 일치를 검사합니다). 다만 스틸컷 빌드는 대사를 자기 파일에서 읽습니다 — 확정 아트 컷 배정과 짝을 맞춘 원고이고 씬 이름 체계도 다릅니다. present_video 행도 파일에서 읽지 않고 createStillcutPresentationContext() 가 코드로 만들어 넣습니다 (clip: none · duration 0 · tap_to_skip 0).

즉 “같은 스토리를 다른 연출로” 비교하려면 이제 두 원고를 함께 관리해야 합니다. 채팅 37행과 스틸컷 48행이 서로 다른 파일이라, 한쪽만 고치면 두 빌드의 내용이 갈립니다.

태스크 루프 머지 1회를 끝낼 때까지 도는 while

단계무슨 일이 일어나나코드
1. 안내 팝업 showPopupTask(node) — 노드 하나만 넘긴다. 팝업은 제목 · 보상 · 초상만 채우고 waitForConfirmation() 으로 기다린다 ViewCreator.showPopupTask
2. 시작 onClickStart() → 약속을 풀고 close(). 중간 판정이 없다 — 곧바로 보드로 내려간다 PopupTask.ts
3. 보드 hideForGameplay() 로 연출을 접고 showViewMergeBoard(node) → waitForCompletion() StoryNodeRunner.playMergeTask
4-a. 완료 머지 1회 → CLEAR 버튼이 켜지고 onClickContinue() → true → 루프를 빠져나가 다음 노드로 ViewMergeBoard.isQuestComplete
4-b. 미완료 뒤로(onClickBack) → false → continue → 1번 팝업부터 다시 ViewMergeBoard.onClickBack
이 루프에는 머지 말고 출구가 없다

보드에서 합치기를 한 번도 안 하고 뒤로 나가면 false 가 돌아와 continue 로 팝업부터 다시 시작합니다. 무한히 반복됩니다. v1.0 의 골드 루프(주문 3회로 26골드)를 BUG-006 에서 “머지 1회”로 통일하면서 회차가 짧아졌을 뿐, 이탈 경로가 없는 구조는 그대로입니다. 실제 게임으로 옮길 때는 이탈 경로가 필요합니다.
