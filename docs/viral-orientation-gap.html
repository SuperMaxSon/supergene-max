③ 할 일 확실한 것부터

1. 초대 지면 늘리기 — 가장 확실하다

초대는 시도 0.81/DAU에 성공률 94.74%입니다. 창이 먹히는 게 이미 증명됐으니 시도를 늘리면 거의 선형으로 늡니다. 지금도 우리 바이럴의 61%를 혼자 만들고 있고, 마종에는 아예 없는 채널입니다.
"성공률이 이미 높은 채널의 시도를 늘린다"가 "성공률이 0인 채널을 고친다"보다 확실합니다. 지면을 어디까지 늘릴 수 있는지가 논점입니다.

2. 메세지 발사 기회 늘리기 — 가장 크고, 생각보다 싸다

격차의 67%이고 쏘면 100% 성공이라 수락률 리스크가 없습니다. FB 창에 의존하지 않으니 가로 문제와도 무관합니다.
코드 조사 결과 — 마종도 매칭 서버가 없습니다. 클라가 전환 성공률 1위 친구를 자동 추천하고 컨텍스트를 무탭 전환할 뿐이고, 로비 PLAY 탭 1회로 P2P 판에 들어갑니다. 그리고 승·패 무관하게 쏩니다(문구도 결과 공유가 아니라 "네 차례야" 턴 유도).
우리 문제는 P2P 상태에 도달하는 길이 둘뿐이라는 것입니다 — FB 메시지를 열고 들어오거나, 리더보드 선물 버튼을 누르거나. 게임 안에서 "친구와 하기"를 고를 방법이 없습니다.

2-1. 가장 싼 안 — 진입점 하나만 추가 (서버 작업 불필요)

솔은 이미 THREAD 컨텍스트 + 상대 ID가 있으면 판 클리어 시 자동으로 쏩니다. 발사 로직을 건드릴 필요가 없습니다 — 그 상태에 도달하는 길만 하나 더 열면 기존 게이트가 그대로 통과됩니다.
로비에 "친구와 하기" 버튼 → 친구 1명 선택 → 기존 PopupSwitchContext.setP2P() 재사용 → 그다음은 평소대로 플레이. 파일 2~4개 · 서버 작업 없음 · 이미 검증된 경로 재사용(리더보드 선물 버튼이 같은 흐름을 씁니다).
단 "어떤 친구를 왜 추천하는가"는 UX 설계가 필요합니다

2-2. 같이 정리할 코드 결함 3개 — 파일 1개

① handleFacebookShare의 case 'p2p':에 break가 없어 case 'tournament':로 fall-through합니다. ② sendDefeatMessage는 호출부 0건 데드코드입니다. ③ sendMessage(..., isRetry) 파라미터가 이미 있는데 true로 부르는 곳이 없어 재시도 로그(3430/3440/3450)가 영원히 0건입니다 — 실패 콜백에서 1회 재호출만 붙이면 됩니다.
세 개 다 FacebookPlatform.ts 한 파일이고, 발사율 격차(7~14배)를 메우진 못하지만 신뢰성은 올립니다.

3. 실기 녹화 — 30분, 배포 0회

Android FB 앱에서 한 판 깨고 생성 창과 초대 창을 나란히 녹화합니다. 확인할 건 둘 — 생성 창의 확인 버튼이 화면 안에 있는가, 초대 창은 왜 되는가(더 작은가). 여기서 크기 가설이 확정되거나 죽습니다.

4. 번들만 PORTRAIT로 바꿔보기 — 빌드 1회

3에서 크기 가설이 확정될 때만 의미가 있습니다. 이것만으로 창이 세로로 뜨면 프리팹 188개를 안 건드리고 끝나고, 안 되면 전면 세로 포팅이라 규모가 완전히 달라집니다. 가능 여부 미확인. 같이 볼 것 — FB App Dashboard의 orientation 값이 번들 fbapp-config.json과 일치하는지(5분).

5. US 데스크톱이 왜 비US의 1/2.6인지 — 미착수

비US Windows 15.65%는 마종과 같은데 US Windows만 6.03%입니다. 모바일 붕괴와 독립된 문제라 따로 봐야 합니다. 후보 — 유저층·FB 앱 버전·브라우저 분포·토너먼트 이웃 밀도. 전부 미검증.

6. 토너 공유율 원인 규명 · 생성 억제 재검토 — 미착수
